- 상태: 초안. 확정 결정(D03·D04·D06·D10·D11)에 근거한 경계와 기술 제안을 구분해 표시하며, 기술 제안은 확정 정책이 아닙니다.
- 작업: SCRUM-7 (이전 DODU-16, 로컬 S1-BE01), 분할 초안 SPLIT-16-3
- 작성: 문은서
- 근거: `docs/dodu/sources/SERVICE_POLICY_v2.5.md` §0·§1·§2·§5, `docs/dodu/sources/FLOW_LOG_MAPPING_v2.5.md` §3~4, `docs/dodu/OPEN_DECISIONS.md` D03·D04·D06·D10·D11(2026-09-27 APPROVED), `docs/dodu/DATA_MODEL.md`, `docs/DEVELOPMENT_CONVENTIONS.md` "API·시간·상태 계약"
- 관련 문서: `docs/api/COMMON_API_CONTRACT.md` 4장 (시간 표현 규칙)

이 문서는 "시간을 어떻게 다루기로 했는가"의 방향만 정합니다. 구현 코드와 클래스 구조는 SCRUM-64에서 이미 시작됐고(`com.dodu.intervention`), 이 문서는 그 방향과 같은 기준을 적습니다.

## 1. 범위

| 이 문서가 정하는 것 | 이 문서가 정하지 않는 것 |
|---|---|
| 기준 시간대와 시각의 저장·전송 방식 | `Clock` 빈 구성, 패키지 위치, 코드 (SCRUM-15 등) |
| 서버가 "현재 시각"을 얻는 방식 | 알림·스케줄러 실행 방식 |
| KST 일자 계산의 책임 | 물리 DB 타입·컬럼 (SCRUM-10) |
| 확정된 시간 경계가 시간 계산에서 어떻게 보이는지 | 경계 정책 자체 (D03·D04·D10·D11이 정함) |

## 2. 기준

1. 서비스의 기준 시간대는 `Asia/Seoul`(KST)입니다. (정책 §0)
2. 서버의 모든 시간 판단은 서버 시각을 기준으로 합니다. 브라우저 시각과 타이머는 안내용입니다. 네트워크 지연과 기기 시계 오차는 서버 시각만으로 없앨 수 없으므로 최종 허용 여부는 서버가 판단하고, UI는 표시 시간대를 `Asia/Seoul`로 명시합니다. (계약 4장 4번, 강민님 기술 제안)
3. 시각은 "시점"과 "KST 일자"를 구분합니다.

| 종류 | 예 | 표현 |
|---|---|---|
| 시점 (언제 일어나는가) | 약속 시작, 인증 마감 | 오프셋 포함 ISO 8601 |
| KST 일자 (며칠의 약속인가) | 같은 날짜 약속 제한(D06)의 기준 날짜 | `YYYY-MM-DD`, 이름은 `...DateKst` |

## 3. 저장·전송 방식

| 구간 | 방식 | 이유 |
|---|---|---|
| API 요청 | 오프셋이 있는 시각만 허용, 없으면 `DATETIME_OFFSET_REQUIRED` | 오프셋 없는 시각은 어느 시점인지 알 수 없음 |
| API 응답 | `+09:00` 오프셋으로 직렬화 (기술 제안, 확정은 강민님 재검토·FE/BE 합의 후) | FE가 사람이 읽는 시각과 맞추기 쉬움 |
| DB 저장 | 모든 업무 시각은 UTC 순간으로 저장하고, KST 일자가 필요한 레코드는 별도 날짜를 보존 (`DATA_MODEL.md`). 물리 타입은 SCRUM-10 | 저장 시점에 시점이 하나로 정해지고 날짜 계산 결과도 남음 |
| 서버 내부 | 시점은 `Instant` 또는 `OffsetDateTime`을 쓰고, 오프셋 없는 `LocalDateTime`은 시점 표현에 쓰지 않음 | 컨벤션의 "시간대 모호성 방지" 방향. `InterventionWindowPolicy`도 `Instant`를 사용 |

`+09:00`으로 쓴 시각과 UTC(`Z`)로 쓴 시각은 표기만 다르고 같은 시점입니다. 응답을 `+09:00`으로 정해도 저장된 시점이 바뀌지는 않습니다.

## 4. 서버가 현재 시각을 얻는 방식

- 서버 코드는 시스템 시계를 직접 부르지 않고, 주입된 `Clock`에서 현재 시각을 얻습니다. (예: `clock.instant()`, `now(clock)` 형태. 인자 없는 `now()`는 쓰지 않습니다.)
- 운영에서는 KST 기준의 시스템 `Clock`을, 테스트에서는 원하는 시각에 고정한 `Clock`을 주입합니다.
- `dev`에는 이미 `Clock`을 생성자로 주입받는 `InterventionWindowPolicy`가 있습니다(SCRUM-64). 예약 범위, 공식 종료, 제출 창 판정을 결정값으로 돌려주고 HTTP 예외는 던지지 않습니다. 같은 규칙을 새로 만들지 않고 이 정책 클래스를 호출하는 쪽으로 정합니다.
- 운영용 `Clock` 빈 설정은 아직 없습니다. 구성 방식은 구현 티켓에서 정합니다. 이 문서에는 코드를 두지 않습니다.

## 5. KST 일자 계산

- "같은 예정 시작일(KST)" 제한(D06) 같은 규칙의 날짜는 **서버가** 시점에서 KST 일자를 계산해 정합니다. 클라이언트가 계산해서 보내거나, 응답을 받아 클라이언트가 다시 계산하지 않습니다.
- 응답에는 계산된 값을 `...DateKst` 필드로 내려줍니다. (계약 4장 3번)
- UTC로 저장된 시점도 KST로 바꿔서 날짜를 정해야 합니다. 아래 예시처럼 UTC 날짜와 KST 날짜가 다를 수 있습니다.

## 6. 변환 예시

값은 모두 가상 데이터입니다.

| 시점 (KST 표기) | 같은 시점 (UTC 표기) | KST 일자 | UTC 날짜와 다른가 |
|---|---|---|---|
| `2026-10-07T20:00:00+09:00` | `2026-10-07T11:00:00Z` | 2026-10-07 | 같음 |
| `2026-10-07T00:30:00+09:00` | `2026-10-06T15:30:00Z` | 2026-10-07 | **다름** |
| `2026-10-07T08:59:00+09:00` | `2026-10-06T23:59:00Z` | 2026-10-07 | **다름** |

두 번째, 세 번째 줄처럼 한국 시간 새벽~오전 9시 이전은 UTC 날짜가 전날입니다. 날짜 제한을 UTC 날짜로 계산하면 이 시간대 약속이 전날로 잡히므로, KST 일자로 계산해야 합니다.

## 7. 확정된 시간 경계 (D03·D04·D06·D10·D11)

T는 약속 시작 시각입니다. 아래는 `OPEN_DECISIONS.md`에서 2026-09-27에 확정된 경계를 시간 계산으로 풀어 쓴 것이며, 이 문서가 정책을 새로 정하는 것이 아닙니다.

| 규칙 | 확정 내용 | 예시 |
|---|---|---|
| 예약 범위 (D11) | `서버 시각 + 5분 ≤ T ≤ 서버 시각 + 72시간`. 생성·수정 모두 적용, 양 끝 모두 허용 | 서버 시각이 `2026-10-06T14:02:11+09:00`이면 `14:07:11`부터(포함) `2026-10-09T14:02:11+09:00`까지(포함). `14:07:10`과 `2026-10-09T14:02:12`는 불허 |
| 공식 종료 (D03) | `T+30 ≤ 공식 행동검증 개입 종료시각`. 종료 후 신규 약속·수정·재생성·복구·알림·개입 중단 | 가상 종료 `2026-10-07T20:30:00+09:00`이면 T=`20:00:00`은 허용, T=`20:01:00`은 불허 |
| 신규 제출 창 (D11) | `T ≤ 서버 접수 시각 < T+30분`. 정확히 T는 허용, T+30은 불가 | T=`20:00:00`이면 `19:59:59` 불허, `20:00:00` 허용, `20:29:59` 허용, `20:30:00` 불허 |
| 수정·취소 (D06) | 서버 시각이 기존 시작 시각 T 이전일 때만 가능. 정확히 T는 불가. 수정은 기존 T의 가능 여부와 새 T의 예약 조건을 따로 검사하고 저장 트랜잭션에서 상태·횟수·동시 충돌을 다시 확인 (응답 코드 `PROMISE_NOT_MODIFIABLE`/409는 기술 제안) | T=`20:00:00`이면 `19:59:59` 수정 가능, `20:00:00` 불가. 사진 제출은 같은 시각이 허용이라 경계가 반대 |
| 접수 후 판정 (D04) | T+30 전에 정상 접수된 제출은 이후에도 판정 가능 | `20:29:59`에 접수된 사진은 `20:31`에 판정이 끝나도 결과를 반영 |
| 판정 중 (D10) | 약속당 동시 Evaluating 사진 최대 1개. Evaluating 중 추가 제출과 T+10/T+20 재알림 차단 | 판정 중이면 `20:10` 재알림은 보내지 않음 |
| 알림 일정 (정책 §3) | T / T+10 / T+20 | T=`20:00`이면 `20:00` / `20:10` / `20:20` |

| 정확히 T인 순간의 수정·취소 | **확정**: 불가 (D06, 계약 7장 Q2). 응답 코드 이름은 기술 제안 |
| 응답 시각 `+09:00` vs UTC | 기술 제안: 이 초안은 `+09:00`으로 작성. 확정은 강민님 재검토·FE/BE 합의 후이며 제품 정책 아님, `Z`와 같은 시점 (계약 7장 Q5) |
| 공식 종료시각의 실제 값 | 이 문서에 값을 두지 않음. 데이터(`STUDY_PERIOD`)로 관리 |

## 9. 테스트 기준

- 시간 규칙 테스트는 고정한 `Clock`으로 실행하고, 실제 시간 경과나 슬립에 의존하지 않습니다.
- 위 7장의 경계값(정확히 +5분, 정확히 +72시간, 정확히 T, T+30 직전·직후, 종료시각 정확히)은 확정 결정이라 테스트로 고정할 수 있습니다. 이미 `InterventionWindowPolicyTests`가 일부를 검증하므로 같은 검증을 중복해서 만들지 않습니다.
- 수정·취소의 정확히 T 경계(불가)는 D06 확정이므로 테스트로 고정할 수 있습니다. 구현은 약속 수정·취소 작업(SCRUM-60)에서 합니다. 응답 시각 표기를 포함한 8장의 기술 제안 항목은 확정 전까지 기대 결과로 고정하지 않습니다.
- `Clock`의 zone과 `Instant`를 구분하고, UTC `Clock`을 쓰더라도 명시적인 KST 날짜 변환을 적용하면 같은 정책 결과여야 합니다 (강민님 기술 제안, 계약 7장 Q5).
- 6장의 KST/UTC 날짜가 달라지는 경우(자정 부근)는 일자 계산을 만드는 구현 티켓에서 별도로 확인할 가치가 있습니다.
