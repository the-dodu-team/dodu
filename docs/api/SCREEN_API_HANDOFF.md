## 2. 모듈별 계약을 작성할 때의 인수 기준

각 모듈은 아래 항목을 채운 후 FE·BE 리뷰를 받는다. 이 지도만으로 SCRUM-76을 완료 처리하거나 모든 후행 티켓의 계약 의존성이 해결되었다고 보지 않는다.

- 요청: method/path, 필수·선택·null, 형식·허용값·크기, 참가자 소유권의 서버 검증 경로.
- 응답: 공통 envelope, 상태별 필수 필드, 식별자·시각·KST 날짜, 빈 결과의 표현. UI 상태와 저장 상태를 구분한다.
- 오류: HTTP/type/code, 안전한 메시지, 현재 상태 재조회 여부. 기술오류와 약속의 TechFailed는 같은 개념이 아니다.
- 동시성: 멱등키의 범위·같은 키/다른 본문 처리·보관기간, 수정 충돌, 지연 응답 및 철회 후 결과 처리. 아직 합의되지 않은 값은 제안으로 남긴다.
- fixtures: 정상·빈 결과·입력 오류·인증 종료·상태 충돌·Evaluating·만료 중 해당하는 사례. 비해당 사례는 이유를 적는다. 가상 데이터만 사용한다.
- 검증: fixture 구조 검사, 승인된 시간 경계, 실제 HTTP/DB 검증을 구분해 증거를 남긴다. JSON이 유효하다는 사실만으로 API 연결 성공이라 하지 않는다.
- 인수: 은서·연정·강민의 모듈별 검토 링크와 미해결 항목을 기록한다. 합의 전 제안을 런타임 기대값으로 고정하지 않는다.

## 3. 정책 경계와 미결정 항목

| 구분 | 적용 기준 / 남은 확인 |
|---|---|
| 승인된 D06·D11 | 예약 `now+5분 ≤ T ≤ now+72시간`, 수정·취소는 기존 T 이전. 정확히 T부터 사진 제출 가능하고 정확히 T+30부터 신규 제출 불가 |
| 승인된 D03·D04·D10 | `T+30 ≤ 공식 개입 종료`. 유효 접수된 사진은 마감 후에도 판정 대기하며 Evaluating 동시 1개. 신규 개입과 기존 접수의 내부 처리를 구분 |
| 승인된 D05·D12 | TechFailed·취소·권한 문제·철회를 정상 미인증과 분리. 자기보고 미응답은 unknown이며 다음 약속 생성 차단 금지 |
| 작업명 | 최신 정책 첨부 §1.3의 최대 30자·단일 행·앞뒤 공백 제거·빈 값 불가를 기준으로 계약 작성. 문자 계수 단위와 공백·제어문자 범위는 FE/BE 기술 합의 필요. 과거 20자·최근 작업명 기능을 복원하지 않음 |
| SCRUM-75 승인 필요 | 온보딩 카메라 요청 vs 정책 §7.3의 첫 촬영 요청, 시스템 기술오류의 T+30 AuthIncomplete 전환, 기술복구 날짜를 오늘로 고정하는 시안 |
| SCRUM-75 확인 필요 | 날짜 선택기가 +72시간 범위를 누락하는지, 기록 조회의 최근 기간과 페이지 방식. 시안만으로 승인된 시간 범위를 축소하지 않음 |
| SCRUM-76 기술 합의 필요 | 시각 직렬화, 엔드포인트·DTO 이름, 판정 결과 polling/이벤트 방식, 멱등키와 오류 코드. 기존 초안을 확정으로 승격하지 않음 |
