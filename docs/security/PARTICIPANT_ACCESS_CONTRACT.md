## 2. 전제와 용어

| 용어 | 뜻 |
|---|---|
| 참가자 코드 | 참가자가 입장할 때 입력하는 비밀 값. 폐쇄형 식별이며 회원가입이 아닙니다. 서버에는 해시만 저장합니다 (`access_credential.secret_hash`) |
| `public_code` | 업무상 가명 식별자 (`participant.public_code`). 비밀 값이 아니며 접근 권한이 없습니다 |
| 기기 식별 상태 | 브라우저에 저장되는 불투명 값. 서버에는 해시로 저장합니다 (`participant_device.device_key_hash`) |
| 세션 | 참가자가 기기에서 입장한 결과로 만들어지는 접근 상태 (`participant_session`) |
| 철회 | 참가자가 연구 참여를 그만두는 것. 운영자가 적용합니다 (§7) |
| 삭제 요청 | 이미 수집된 데이터를 지워 달라는 요청. **철회와 별도**입니다 (§8) |
| 재발급 | 분실·노출된 참가자 코드를 폐기하고 새 코드를 발급하는 것 (§5) |

**[확정]** 폐쇄형 참가자 식별입니다. 정식 회원가입과 소셜 로그인은 범위에서 제외합니다 (`IMPLEMENTATION_CONTEXT.md`).

## 3. 입장과 세션

### 3.1 입장 흐름 (S01-1)

1. 참가자가 코드를 입력합니다. **[확정]** 영숫자 입력, 형식 검증, 입력이 비면 [입장하기] 비활성 (디자인 S01-1).
2. 서버가 코드 해시를 검증합니다. **[제안]** 아래 결과 중 하나로 응답합니다.

| 서버 판단 | 이동 화면 | 근거 |
|---|---|---|
| 유효 + 최초 입장 | 온보딩 S02-1 | **[확정]** 디자인 S01-1 |
| 유효 + 온보딩 완료 | 홈 S03-1/S03-2 | **[확정]** 디자인 S01-1 |
| 행동검증 종료 이후의 코드 | S13 종료 화면 (이 화면만 노출) | **[확정]** 디자인 S13, 정책 만료 |
| 무효·만료·폐기 코드 | 입력창 아래 오류 문구 | **[확정]** 디자인 S01-1 |
| 철회한 참가자의 코드 | 화면 미정 | **[확인필요]** §7.4 |

3. **[제안]** 무효, 만료, 폐기된 코드는 **같은 응답**을 돌려줍니다. 디자인도 "유효하지 않거나 만료된 코드예요"로 한 문구를 씁니다. 코드가 존재했는지, 어떤 사유로 막혔는지를 구분해 알려주면 코드 대입 공격에 정보를 줍니다.

### 3.2 코드의 강도 — 보안상 가장 먼저 확인할 점

디자인의 입력 예시는 `PT-0231`입니다. 이 형식이 **비밀 값 자체**라면 숫자 4자리(1만 가지)라서 다른 사람이 코드를 대입해 볼 수 있습니다. 이 티켓의 검증 시나리오 "타인 식별자 대입"에 해당합니다.

| 항목 | 내용 |
|---|---|
| 현재 상태 | `PT-0231`이 비밀 값인지 `public_code`인지 문서에서 구분되지 않습니다. DATA_MODEL_GUIDE는 `public_code`를 비밀이 아닌 가명 식별자, 참가자 코드를 `access_credential`의 비밀 자격으로 둡니다 |
| **[확인필요]** | 입장 코드의 형식과 길이, 발급 방식 (엔트로피), 해시 알고리즘. DATA_MODEL_GUIDE도 "미정"으로 둡니다 |
| **[제안]** | 입장 코드는 `public_code`와 **분리**하고, 추측이 어려운 무작위 값으로 발급합니다. 사람이 읽고 입력할 수 있는 길이(예: 혼동 문자 제외 10자 이상)를 기준으로 하되 구체 값은 강민님이 정합니다 |
| **[확정]** | 입장 실패 시도 제한은 SCRUM-70에서 정해졌습니다(사용자 승인 2026-10-08): 같은 IP에서 참가자 코드 입력 실패가 10분 안에 10회면 15분 동안 임시 차단하고, 차단 중 요청은 만료 시각을 연장하지 않습니다. 사진 재시도에는 적용하지 않습니다. 순수 정책 코드와 단위 테스트는 완료됐고(커밋 7ec3df2, 강민님), 실제 입장 API 연결은 SCRUM-56에 의존합니다. 이 문서는 정책을 새로 정하지 않고 SCRUM-70을 따릅니다 |
| **[제안]** | 제한에 걸린 응답은 `TECHNICAL`이 아닌 별도 코드 `TOO_MANY_ATTEMPTS`(429)와 `Retry-After`로 구분합니다. 코드 이름은 PR #9 확정 후 반영합니다 |
| **[확인필요]** | IP 외에 같은 코드 접두 단위의 제한이 필요한지는 코드 강도(위 항목)가 정해진 뒤 판단합니다. SCRUM-70 정책에는 포함되어 있지 않습니다 |
| **[제안]** | 코드, 세션 토큰, 구독 키는 로그·오류 메시지·URL에 남기지 않습니다 |

### 3.3 세션과 기기

**[확정]** (0928 정책, `IMPLEMENTATION_CONTEXT.md`, `DATA_MODEL.md` 규칙 11~12)

- 참가자 코드는 여러 기기에서 재사용할 수 있습니다.
- 참가자당 활성 기기·세션은 1개입니다.
- 새 기기에서 입장하면 기존 세션과 알림 구독이 종료되고 새 세션·구독이 활성화됩니다.
- 같은 기기 재진입은 저장된 기기 식별 상태를 사용합니다 (코드를 다시 입력하지 않습니다).
- 약속·인증·자기보고·행동 로그는 세션·기기가 아닌 `participant_id`에 귀속합니다.
- DB에는 참가자당 `Active` 세션이 1개만 존재하도록 부분 유니크 인덱스(`ux_participant_session_one_active_per_participant`)가 있습니다.

**[제안]** 동시에 두 기기에서 입장하는 경우, 앞의 인덱스가 마지막 방어선입니다. 서버는 "기존 활성 세션 종료 → 새 세션 생성"을 하나의 트랜잭션으로 처리하고, 인덱스 위반이 나면 한 번 재시도한 뒤 실패하면 `CONFLICT`로 응답합니다.

**[제안]** 종료된 세션으로 오는 요청은 401로 응답하되 사유를 구분합니다.

| 사유 | 제안 코드 | 화면 |
|---|---|---|
| 다른 기기 입장으로 종료 | `SESSION_REPLACED` | **[확인필요]** FE 안내 문구 (예: "다른 기기에서 이용 중이에요") |
| 코드 폐기·재발급으로 종료 | `CREDENTIAL_REVOKED` | **[확인필요]** 코드 재입력 화면으로 |
| 만료·토큰 없음·알 수 없는 토큰 | `ACCESS_REQUIRED` | 코드 입력 화면으로 |

`SESSION_REPLACED`와 `CREDENTIAL_REVOKED`는 PR #9의 Q7 질문과 같은 항목입니다. PR #9가 확정되기 전까지는 제안입니다.

### 3.4 iPhone 홈 화면 앱과 Safari 브라우저는 다른 기기로 보입니다

디자인 S02-1A는 "브라우저에서 입력한 정보는 홈 화면 앱으로 이어지지 않아요. 홈 화면 앱에서 참가자 코드를 한 번 더 입력해주세요"라고 안내합니다. 서버 쪽에서는 아래와 같이 됩니다.

1. Safari에서 코드를 입력해 세션 A가 만들어집니다.
2. 홈 화면 앱에서 코드를 다시 입력하면 저장소가 달라서 **새 기기**로 인식합니다.
3. 세션 A와 그 알림 구독이 종료되고 홈 화면 앱의 세션 B가 활성화됩니다.
4. 알림 구독은 세션 B가 생긴 뒤 홈 화면 앱에서 등록해야 합니다 (iPhone은 홈 화면 앱이어야 알림을 받을 수 있습니다).

이 흐름은 정책 위반이 아니라 **의도된 결과**입니다. 다만 QA 시나리오에 넣어야 합니다 (§10, S-07). 비공개(시크릿) 모드도 매번 새 기기로 보이므로 **지원 환경에서 제외하는 안**을 권장합니다 (**[확인필요]** 지원 환경은 정책 §14에 따라 기술 검토·QA 후 확정).

### 3.5 세션 설정값

| 항목 | 상태 | 내용 |
|---|---|---|
| 세션 만료 시간 (`expires_at`) | **[확인필요]** | 권장: 행동검증 접근 종료 시각을 상한으로 하고, 사용자 조작이 없어도 유지합니다. 사용자가 며칠 만에 알림을 눌러 들어오는 사용 방식이라 짧은 만료는 맞지 않습니다 |
| 세션 토큰 전달 방식 | **[확인필요]** 강민님 | 쿠키 또는 Authorization 헤더. 쿠키라면 `HttpOnly`, `Secure`, `SameSite`와 CSRF 대응이 필요합니다. 홈 화면 앱·푸시 환경을 고려해 결정합니다 |
| 토큰 형식 | **[제안]** | 서버 조회형 불투명 토큰(해시 저장). 자체 서명 토큰(JWT)은 즉시 폐기가 어려워 이 정책(세션 교체, 철회, 재발급)과 맞지 않습니다 |

## 4. 인가: 자기 데이터만 보게 하는 규칙

- **[제안]** 모든 참가자용 API는 요청에서 `participant_id`를 받지 않습니다. 세션이 가리키는 참가자만 사용합니다. 경로나 본문에 다른 참가자의 ID를 넣어도 무시하거나 거부합니다.
- **[제안]** 약속, 인증 시도, 사진, 자기보고 같은 자원은 조회할 때 항상 "세션의 참가자 소유인가"를 조건에 포함합니다.
- **[제안]** 소유자가 다른 자원은 **존재하지 않는 자원과 같은 404 응답**(`RESOURCE_NOT_FOUND`)으로 처리합니다. 403으로 답하면 해당 ID의 자원이 있다는 사실이 드러납니다.
    - 현재 SCRUM-7 초안은 `ACCESS_FORBIDDEN`(403)에 "타인 데이터 접근 차단"이라고 적어 두었습니다. 이 제안을 채택하면 그 줄의 설명을 바꿔야 하며, **[확인필요]** 강민님·FE 확인 후 PR #9 머지 뒤 반영합니다.
    - 403은 "로그인한 참가자이지만 이 동작이 허용되지 않는 상태"(예: 종료 후 신규 동작)에만 남깁니다. 단 종료 후 신규 동작은 SCRUM-7에서 이미 `STUDY_PERIOD_ENDED`(409)로 정해 두었으니 중복되지 않게 정리가 필요합니다.
- **[제안]** 사진은 공개 URL을 만들지 않습니다 (`photo_asset.storage_key`는 내부 식별자). 사진 조회 기능이 생기면 세션 확인을 거치는 응답으로만 제공합니다.

## 5. 코드 재발급·폐기

**[확정]** 코드 분실·노출 시 기존 접근 자격을 폐기하고 교체 자격을 발급합니다. 최초 발급에는 이전 자격이 없고, 이전 자격을 두 번 대체하거나 다른 참가자의 자격과 연결하지 않습니다 (`DATA_MODEL.md` 규칙 13, GUIDE 8번).

| 항목 | 상태 | 내용 |
|---|---|---|
| 폐기와 발급의 원자성 | **[제안]** | 하나의 트랜잭션. `access_credential.revoked_at` 기록 + 새 행 생성 + `replaces_credential_id` 연결 |
| 폐기된 코드로 새 입장 | **[제안]** | 거부 (§3.1과 같은 응답) |
| **재발급 시 열려 있는 세션** | **[확인필요]** | **권장: 같은 트랜잭션에서 세션과 알림 구독을 모두 종료합니다.** 이유: 코드가 노출됐다면 제3자가 이미 세션을 만들었을 수 있고, 세션이 남으면 재발급이 의미 없습니다. 반대로 코드가 노출되지 않은 단순 분실이라면 세션을 유지해도 됩니다. 이 둘을 서버가 구분할 수 없으므로 일관되게 종료하는 편이 안전합니다. 참가자는 새 코드로 다시 입장하면 되고, 데이터는 `participant_id`에 남아 있어 잃지 않습니다 |
| 누가 재발급을 시작하나 | **[확인필요]** | 참가자 요청 → 운영자가 실행하는 구조를 제안합니다. 참가자가 앱에서 직접 재발급하는 기능은 만들지 않습니다 (본인 확인 수단이 없음) |
| 재발급된 코드 전달 방법 | **[확인필요]** | 운영 채널로 직접 전달. 발급 직후 한 번만 보여주고 서버에는 해시만 남깁니다 |
| 재발급 횟수 제한 | **[확인필요]** | 제한 여부. 제한이 없으면 운영 부담만 늘어날 뿐 보안 위험은 작습니다 |

**참고 — 새 기기에서 같은 코드를 쓰는 것은 코드 노출과 구분되지 않습니다.** 제3자가 노출된 코드를 새 기기에서 입력하면 정상 참가자의 세션이 종료됩니다. 이런 일이 생기면 정상 참가자는 `SESSION_REPLACED`를 받고 운영자에게 알려 재발급을 받게 됩니다. 그래서 `SESSION_REPLACED` 안내 문구에 "본인이 아니라면 운영자에게 알려주세요" 같은 안내를 넣을지 **[확인필요]** (FE).

## 6. 접근이 거부되는 경우 정리

| 상황 | 유형 | HTTP | 코드(제안) | 화면 |
|---|---|---|---|---|
| 세션 없음·알 수 없는 토큰·세션 만료 | UNAUTHENTICATED | 401 | `ACCESS_REQUIRED` | 코드 입력 S01-1 |
| 다른 기기로 교체됨 | UNAUTHENTICATED | 401 | `SESSION_REPLACED` | **[확인필요]** |
| 코드 폐기·재발급으로 종료 | UNAUTHENTICATED | 401 | `CREDENTIAL_REVOKED` | **[확인필요]** |
| 입장 시 무효·만료·폐기 코드 | UNAUTHENTICATED | 401 | `ACCESS_CODE_INVALID` (세 경우 동일 응답) | S01-1 오류 문구 |

- 코드 이름은 모두 **[제안]**입니다. 공통 계약의 오류 코드 목록(3.5)은 PR #9가 확정된 뒤에 추가합니다.
- 카메라·알림 권한 거부는 브라우저 상태이므로 서버 오류 코드로 만들지 않습니다 (SCRUM-7, 정책 §7.3 · D05).

### 6.1 행동검증 종료 이후의 접근

- **[확정]** 공식 개입 종료 후 신규 약속·수정·재생성·기술복구·알림·개입은 중단됩니다. 이미 접수된 유효 제출과 개별 자기보고(24시간 응답)는 완료할 수 있습니다 (D03).
- **[확정]** 접근은 마지막 자기보고 창이 끝난 뒤에 종료됩니다 (운영 정책). 종료 후 코드로 들어오면 S13만 보입니다.
- **[제안]** 따라서 개입 종료와 접근 종료 사이에는 세션이 유효하되 허용 동작은 "이미 접수된 제출의 결과 확인, 자기보고 응답, 기록 조회"로 제한합니다. 이 구간의 허용 목록은 SCRUM-22/23 명세에서 표로 닫습니다.
- **[확인필요]** `study_period.access_ends_at`이 위 "마지막 자기보고 창 이후"를 뜻하는지(= 참가자별 마지막 창이 아니라 연구 전체의 마감인지) 정의가 필요합니다. 참가자마다 마지막 약속 시각이 달라 "마지막 자기보고 창"이 개인마다 다를 수 있기 때문입니다.

### 6.2 Jira 티켓 문구와의 차이

SCRUM-12(DODU-21) 티켓은 "공식 종료 후 접근과 최종 상태·설문 적격성은 D03/D05/D12 대기로 남긴다"고 적고 있습니다. 그러나 `OPEN_DECISIONS.md`에서는 D03·D05·D12가 2026-09-27 **APPROVED**입니다. 이 문서는 승인된 기록을 기준으로 쓰고, 티켓 문구는 갱신이 필요한 오래된 표기로 봅니다. **[확인필요]** 강민님 확인 후 티켓 설명을 수정합니다.

## 7. 철회

### 7.1 정책

**[확정]** 운영 정책(첨부본) 기준입니다.

- 철회는 **운영자가 적용**합니다. 참가자가 앱에서 직접 철회하는 화면은 없습니다.
- 철회가 적용되면 알림, 자기보고, 수집이 중단되고 접근이 비활성화됩니다.
- 진행 중인 활성 약속은 `Withdrawn`으로 종료됩니다 (D05).
- 철회 이후 도착하는 비동기 결과(사진 판정 등)는 상태에 반영하지 않습니다.
- 철회와 과거 데이터 삭제 요청은 구분합니다 (§8).
- **[확정]** 철회와 약속 취소는 다릅니다. 약속 취소는 참가자가 T 이전에 하는 일이고, 철회는 참여 자체를 끝내는 일입니다.

### 7.2 적용 순서 (제안)

철회는 한 트랜잭션에서 처리해, 일부만 적용된 상태가 남지 않게 합니다.

| 순서 | 동작 | 사용하는 값 |
|---|---|---|
| 1 | 참가자를 철회 상태로 변경, `withdrawn_at`·`access_disabled_at` 기록 | `participant` |
| 2 | 활성 세션과 알림 구독 종료 | `participant_session`, `notification_subscription` |
| 3 | 활성 접근 자격 폐기 | `access_credential.revoked_at` |
| 4 | 활성 약속을 `Withdrawn`으로 종료 | `promise.lifecycle_status` |
| 5 | 예약된 알림·자기보고 작업 무효화 | 스케줄러 (§7.3) |

### 7.3 늦게 도착하는 결과로부터 보호하기

철회 직전 제출된 사진의 판정이 철회 이후에 끝날 수 있습니다.

- **[제안]** 판정 결과를 저장하기 직전에 참가자의 철회 여부와 약속 상태를 다시 확인하고, 철회 상태면 결과를 약속 상태에 반영하지 않습니다.
- **[제안]** 스케줄 작업(T 알림, T+10/T+20 재알림, 자기보고 Push)은 실행 직전에 참가자 상태를 확인합니다. 이는 SCRUM-7 컨텍스트의 "실행 직전 재확인"과 같은 방식입니다.
- **[확인필요]** 철회 이후 도착한 결과를 **저장은 하되 반영하지 않을지**, **저장하지 않을지**. 삭제 요청과의 관계가 있어서 정책 결정이 필요합니다. 권장: 약속 상태에는 반영하지 않고, 원시 기록으로도 남기지 않습니다 (수집 중단 원칙).

### 7.4 열려 있는 질문

| 질문 | 추천 |
|---|---|
| 철회한 참가자가 같은 코드로 입장하면 어떤 화면을 보여주나 | 이 경우에 대한 디자인 화면이 없습니다. 무효 코드와 같은 응답으로 처리하면 사용자가 이유를 알 수 없습니다. 별도 안내가 필요하면 FE와 협의가 필요합니다 |
| 철회 적용 기준 시각 | 운영자가 DB에 반영한 `withdrawn_at`을 기준으로 합니다. 참가자가 철회를 요청한 시각과 차이가 생길 수 있어, 요청 시각을 따로 기록할지 결정이 필요합니다 |
| 철회한 참가자의 재참여 | 가능 여부를 정책으로 정해야 합니다. 가능하면 새 참가자로 등록할지, 기존 `participant_id`를 되살릴지도 함께 정해야 합니다. 통계 분리를 위해 새 참가자로 만드는 쪽을 권장합니다 |

## 8. 삭제 요청

### 8.1 정책

**[확정]** 운영 정책(첨부본) §13 상당, `IMPLEMENTATION_CONTEXT.md`:

| 항목 | 내용 |
|---|---|
| 삭제 대상 | 사진, 이벤트 원시 데이터, 자기보고 응답, 식별 연결 정보 |
| 남을 수 있는 것 | 재연결이 불가능한 익명 집계 |
| 보관 기간 | 사진은 공식 종료 후 최대 30일, 연결된 행동 원시 데이터는 종료 후 최대 90일 |
| 철회와의 관계 | 별도 요청. 철회했다고 데이터가 자동 삭제되지는 않고, 삭제 요청이 있으면 삭제합니다 |

### 8.2 처리 방식 (제안)

`DATA_MODEL_GUIDE.md`의 완전 삭제 순서를 따릅니다.

1. 삭제 요청을 접수하면 같은 참가자의 신규 수집·재생성을 막습니다.
2. 사진·파생본을 먼저 찾아 제거합니다 (파일과 버전이 지워진 것을 확인한 뒤 메타데이터 행과 키를 삭제합니다).
3. 사진 참조, 설문, 이벤트, 알림 기록, 시도, 일정 이력, 약속, 권한 이력, 접근 자격을 순서대로 정리합니다.
4. 실패한 항목은 재시도 대상으로 유지하고 완료로 표시하지 않습니다.
5. 완료 시 `data_request` 행에는 식별자·작업명·파일 키를 남기지 않고 상태·시각·안전한 오류 코드만 둡니다 (`DATA_MODEL.md` 규칙 10).
6. 익명 집계와 삭제 대상 원시 데이터는 저장 영역과 접근 권한을 분리합니다 (규칙 7).

### 8.3 열려 있는 질문

| 질문 | 상태 | 내용 |
|---|---|---|
| 삭제 요청 처리 사실을 어디까지 남기나 | **[확인필요]** | 권장: 요청 접수 시각, 완료 시각, 결과(성공/실패)만 남기고 참가자 식별 정보는 지웁니다. 이 기록을 얼마나 오래 보관할지는 정책 결정이 필요합니다 |
| "식별 연결 정보"의 범위 | **[확인필요]** | 참가자 코드·`public_code`와 데이터를 이어 주는 정보를 말합니다. 접근 자격 해시, 기기 식별 해시, 세션, 구독, `participant`와 `public_code`의 연결이 포함되는지 목록으로 정해야 합니다 |
| 삭제 요청 시 접근도 종료되나 | **[확인필요]** | 권장: 삭제 요청을 접수하면 철회가 안 된 경우에도 접근을 비활성화합니다. 삭제하는 중에 새 데이터가 쌓이면 삭제가 끝나지 않기 때문입니다 |
| 90일 원시 데이터와 익명 집계의 경계 | **[확인필요]** | 집계가 "재연결 불가능"하다는 기준 (최소 인원 등)을 정해야 합니다 |

## 9. 운영자 기능

**[확정]** 철회는 운영자가 적용합니다. 참가자용 철회 화면은 없습니다.

운영자가 하는 일은 아래 네 가지입니다. 화면은 디자인에 없고, 도구와 인증 방식은 정해지지 않았습니다.

| 작업 | 영향 |
|---|---|
| 참가자 등록·코드 최초 발급 | `participant`, `access_credential` 생성 |
| 코드 재발급 | §5 |
| 철회 적용 | §7 |
| 삭제 요청 처리 | §8 |

| 안 | 내용 | 장단점 |
|---|---|---|
| A. 운영 스크립트 | 승인된 사람이 서버에서 실행하는 스크립트와 실행 절차서 | 구현이 작고 외부 노출 면이 없음. 실행 기록을 남기는 규칙이 필요함 |
| B. 내부 관리 API | 별도 인증을 둔 운영자 전용 API | 편하지만 운영자 인증·권한 체계를 새로 만들어야 하고 공격 면이 늘어남 |

- **[제안]** 참가자 수가 적은 검증 단계에서는 **A안**으로 시작합니다. B안은 운영 요구가 늘어날 때 추가합니다. **[확인필요]** 강민님.
- **[제안]** 어느 안이든 운영자 작업은 감사 기록을 남깁니다 (누가, 언제, 어떤 참가자에게, 어떤 작업을). 이 기록에도 코드·토큰 원문은 남기지 않습니다. 감사 기록 저장 위치는 V1에 없어 V2 테이블 또는 별도 로그로 정해야 합니다.

## 11. 스키마 영향 (SCRUM-10 V1 기준)

V1에 이미 있는 것: `access_credential`, `participant_device`, `participant_session`, `notification_subscription`, 참가자당 활성 세션 1개를 보장하는 부분 유니크 인덱스.

| 필요한 것 | V1 상태 | 비고 |
|---|---|---|
| 철회·접근 종료 상태값 | 있음(`participant.lifecycle_status`) | 값이 미정(OPEN). 철회와 접근 만료를 구분 (D05) |
| 세션 종료 사유 | 있음(`revoke_reason`) | 값 미정. 위 3.3의 코드와 연결됨 |
| 삭제 요청 처리 기록 | **없음**(`data_request` 제외) | 삭제 기능 구현 전 V2 필요 |
| 입장 시도 횟수 제한 저장소 | 없음 | SCRUM-70에서 다룹니다. 공유 저장소·신뢰 프록시 IP·다중 서버는 SCRUM-70의 미완료 항목입니다 |
| 운영자 작업 감사 기록 | 없음 | V2 또는 로그 |
| 권한 상태 기록 | **없음**(`participant_permission` 제외) | 화면 S12 권한 거부 보고에 필요 |

적용이 끝난 마이그레이션은 수정하지 않고 V2 이상으로 추가합니다.
