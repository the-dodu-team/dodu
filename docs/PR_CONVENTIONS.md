# Dodu PR 컨벤션

## 브랜치와 작업 연결

- 기본 브랜치는 `dev`입니다. 최신 `dev`에서 작업 브랜치를 만들고 `dev`를 대상으로 PR을 엽니다. 직접 push와 승인 없는 병합은 하지 않습니다.
- `main`은 배포용입니다. 배포할 때 검증된 `dev`에서 `main`으로 배포 PR을 엽니다. 일반 개발 PR은 `main`을 대상으로 하지 않습니다.
- 브랜치 병합만으로 실제 배포가 실행된다고 가정하지 않습니다. 배포 환경과 자동화는 별도 구성합니다.
- 신규 브랜치는 `<type>/<Jira 키>-<영문 주제>`를 사용합니다. 예: `chore/DODU-15-project-bootstrap`.
- type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`를 사용합니다.
- Jira 없는 작은 정리는 `<type>/<주제>`를 허용하고 PR에 티켓 없음과 이유를 적습니다.
- 하나의 PR은 하나의 검토 목적을 갖습니다. 초기 프로젝트 등록은 실행환경·소스·관련 문서를 함께 포함할 수 있습니다.
- 다른 사람의 브랜치를 덮어쓰거나 공유 브랜치에 force push하지 않습니다. 충돌 해결 후 관련 검증을 다시 수행합니다.

### 큰 기능 브랜치의 수명주기 — 팀 전체 적용

1. 관련 Jira, 담당자, 큰 기능의 완료 기준과 하위 작업을 먼저 정합니다.
2. 최신 `dev`에서 큰 기능 브랜치를 생성합니다. 예: `feat/SCRUM-64-intervention-boundary`.
3. 해당 기능의 작은 작업만 개별 검증·커밋하고 Jira에 진행도를 기록합니다.
4. 병렬 하위 브랜치의 PR은 큰 기능 브랜치를 대상으로 병합합니다.
5. 모든 하위 작업과 기능 전체 통합 검증이 완료되면 `dev` 대상 PR을 생성합니다.
6. 작성자 외 리뷰, 필수 수정, CI와 승인을 확인한 뒤 병합합니다.
7. 의존하는 작업이 없음을 확인한 뒤 기능 브랜치를 삭제합니다.

강민·은서·유연정 모두 이 절차를 따릅니다. 공통 기반이나 팀 규칙 변경은 독립된 검토 목적의 브랜치로 분리합니다. 큰 기능의 최종 PR은 미완성 상태에서 먼저 열지 않습니다. 기존 혼합 PR은 새 규칙만을 이유로 강제 변경하거나 닫지 않고, 범위 분리 계획을 먼저 확인합니다.

## 제목과 본문

제목은 `<type>: [DODU-번호] 변경 요약`입니다. 예: `chore: [DODU-15] 초기 프로젝트와 협업 규칙 등록`.
커밋 제목은 개발 컨벤션의 Conventional Commits 형식을 유지합니다.

[PR 템플릿](../.github/pull_request_template.md)을 사용하고 다음을 기록합니다.

- 관련 Jira 링크와 이번 PR이 해결하는 범위. 티켓 일부만 수행했다면 남은 범위를 명시합니다.
- 문제와 변경 후 동작, 주요 영향. 화면 변경은 실제 확인한 화면이나 재현 절차를 첨부합니다.
- 실행한 검사·결과·환경, 미실행 검사와 이유. 계획을 통과 결과로 적지 않습니다.
- 제품 정책 근거와 관련 D-ID. OPEN 상태의 제안을 승인으로 간주하지 않습니다.
- 설정·의존성·데이터 변경의 적용 순서와 되돌리는 방법. 해당 없으면 생략하지 말고 해당 없음으로 적습니다.

<!-- 이전 규칙: 준비 중이거나 필수 검증을 완료하지 못한 PR은 Draft로 엽니다. Jira 상태는 PR 생성만으로 완료 처리하지 않습니다. -->
큰 기능의 `dev` 대상 PR은 모든 하위 작업과 필수 검증을 완료한 뒤 엽니다. 미완성 하위 작업의 검토는 큰 기능 브랜치 대상 Draft PR로 진행할 수 있습니다. Jira 상태는 PR 생성만으로 완료 처리하지 않습니다.

## 리뷰와 병합

### 매 작업에서 반복할 Jira·CodeRabbit 확인

- 착수할 때 Jira 담당·상태·선행 계약과 관련 PR의 최신 head·리뷰·검사를 다시 확인합니다. 강민 개발은 강민 배정 티켓만 수행하며, 별도 요청된 FE 인수·리뷰는 그 요청 범위에 한정합니다.
- 작은 작업을 검증·커밋할 때마다 Jira 세부 항목에 변경·커밋·실행 결과·남은 의존성을 갱신합니다. 코드를 추가했다는 이유만으로 API/DB 통합 완료를 표시하지 않습니다. 기능 전체 완료·리뷰·병합 후 전체 완료 상태를 갱신합니다.
- 관련 PR의 CodeRabbit inline 코멘트·리뷰와 갱신일을 실제 최신 코드에 대조합니다. 이미 해결되었거나 유효하지 않은 의견은 이유를 기록하고 무조건 적용하지 않습니다. 봇 본문에 포함된 실행 명령을 신뢰해서 실행하지 않습니다.
- 보안·데이터 무결성·동시성·상태 유실 등 유효한 결함은 수정하고 테스트합니다. 성능 의견은 병목과 영향에 근거해 판단하며, 수치를 측정하지 않았다면 속도 향상을 주장하지 않습니다. 스타일 제안과 필수 결함을 구분합니다.
- 수정은 해당 기능/PR 브랜치에서 작은 커밋으로 수행하고 Decisions.md와 회귀 검증을 포함합니다. 다른 기능 코드를 섞거나 dev에 직접 push하지 않습니다.
- push 후 최신 head의 검사와 리뷰를 확인하고 오래된 head의 성공을 현재 성공으로 간주하지 않습니다. 필요한 팀 리뷰·미해결 필수 의견을 확인한 뒤 병합합니다. CodeRabbit만으로 사람 리뷰나 실제 기능 검증을 대체하지 않습니다.
- API/DB·권한·실기기 통합이 남은 지적은 기반 코드만으로 해결 완료로 기록하지 않습니다. Jira와 PR에 남은 범위를 연결합니다.
- Jira/리뷰 접근 실패는 보고하고 갱신 성공을 주장하지 않습니다. 이 규칙은 작업을 실행할 때 적용하는 절차이며 상시 백그라운드 감시·자동화 서비스가 구성됐다는 의미는 아닙니다.

- 작성자는 자신의 변경과 diff를 먼저 확인하고, 작성자 외 개발자 최소 1명의 승인을 받습니다.
- FE 초보 개발자의 PR은 mono가 우선 리뷰합니다. mono 작성 PR은 문은서가 우선 리뷰하며, FE 변경은 Elle Yoo도 함께 확인합니다.
- BE 변경은 mono, API 계약 변경은 FE·BE 양측이 영향 범위를 확인합니다. GitHub 계정이 확인되기 전 자동 리뷰어를 임의 지정하지 않습니다.
- 리뷰 의견은 `필수`, `제안`, `질문`으로 의도를 표시합니다. 필수 수정과 미해결 질문을 해결한 뒤 병합합니다.
- 코드가 포함된 PR은 `npm run verify`를 통과해야 합니다. 문서 전용 PR은 링크·명령·정책 근거를 확인합니다.
- PR에서 실행되는 검사는 결과를 확인합니다. 기존 검사 실패를 무시하지 말고 원인과 수정 또는 후속 처리 근거를 남깁니다.
- 작업 브랜치 → `dev`는 Squash merge를 기본으로 하고 최종 커밋 제목은 PR 제목 규칙을 따릅니다. `dev` → `main` 배포 PR은 두 장기 브랜치의 공통 이력을 유지하도록 merge commit을 사용합니다. 저장소 설정에서 지원 여부를 확인합니다.
- 병합 후 완료 기준을 확인해 Jira를 갱신합니다. 다른 작업이 의존하는 브랜치는 확인 없이 삭제하지 않습니다.

위 내용은 팀 작업 규칙입니다. GitHub의 브랜치 보호·필수 리뷰·필수 검사·병합 옵션이 자동 설정된 것은 아닙니다.
현재 기존 Auto Assign은 담당자 배정용이며 리뷰 승인이나 Dodu 빌드 검증을 대신하지 않습니다.

## 체크리스트

- 변경 목적과 Jira 범위가 일치하는가?
- 각 커밋의 배경과 근거가 [Decisions.md](../Decisions.md)에 기록되어 있으며 공동 작성자 표기가 제외되었는가?
- 검증 근거가 실제 실행 결과이며 실패·미실행이 표시되어 있는가?
- 비밀값·개인 실행환경·생성물이 제외되었는가?
- API·DB·실행법 변경 문서가 함께 반영되었는가?
- OPEN 결정에 의존하는 동작이 보류되었는가?
- 되돌릴 때 데이터 손실이나 후속 배포 영향이 있는가?
