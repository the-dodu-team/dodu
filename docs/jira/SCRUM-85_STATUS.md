## 2026-11-23 Render 개선 후 측정

- 조건: PR #58 배포(Render active 확인) 후, 개선 전과 같은 스크립트·같은 거절용 사진(실행마다 해시만 다르게)·제출 전 0~30초 무작위 대기로 20회.
- 결과(정상 19건, 모두 `Rejected`/`AI_OTHER`):

| 항목 | 개선 전(2026-11-20, 20건) | 개선 후(19건) |
|---|---|---|
| 판정 시작까지 대기(`decidedAt - requestReceivedAt`) | 평균 16.3초·p95 31.2초 | 평균 1.5초·p95 4.3초 |
| 처리(사진 읽기+AI+저장) | 평균 3.0초 | 평균 3.2초 |
| 업로드 응답 | 평균 3.1초 | 평균 2.5초 |
| 제출→판정 | 평균 22.3초·p95 36.4초 | 평균 7.2초·p95 19.2초 |
| 제출→화면(FE 3초 확인 주기 반영) | 평균 23.8초·p95 38.5초 | 평균 9.0초·p95 20.2초 |

- 해석: 30초 주기 대기가 사라져 제출→화면 평균이 약 62% 줄었다. p95는 첫 건(처리 9.7초, 유휴 후 첫 요청으로 추정) 영향이며 첫 건 제외 시 평균 8.3초. 개선 후의 대기 1.5초는 워커 대기가 아니라 접수 시각부터 저장·커밋·차지까지의 시간이다. 남은 시간은 업로드 약 2초·처리 약 3초·FE 3초 확인 주기.
- 미해결: 11번째 제출이 `500 INTERNAL_ERROR`. 저장소 오류(503)·중복 요청(409)이 아닌 예기치 않은 예외로, 원인은 Render 런타임 로그(2026-11-23 05:05~05:15 UTC 전후) 확인 필요. Render 계정 담당자 확인 대기.
- Jira: 500 원인 확인 전까지 SCRUM-85 상태 변경 없음.

## 2026-11-22 Render 시작 실패 수정

- 원인: PR #57의 즉시 판정 실행기 빈 때문에 Spring Boot 기본 `applicationTaskExecutor`가 생성되지 않아, FCM이 켜진 운영에서 `DeviceChangeNotificationListener` 생성 실패로 서버가 시작하지 못했다(배포 실패, 이전 빌드 유지).
- 수정: 실행기를 빈으로 등록하지 않고 디스패처가 직접 만들고 종료한다. 근거 Decisions DEV-20261122-02.
- 검증: 회귀 테스트 추가, 백엔드 전체 327건 통과(건너뜀 1). Render 배포 성공·개선 후 측정은 미확인.

## 2026-11-22 사진 제출 직후 판정 시작

- 원인: 판정은 30초 주기 워커에서만 시작되어 Render 측정(20회)에서 워커 대기가 평균 16.3초·p95 31.2초로 전체(제출→화면 평균 23.8초)의 대부분이었다. 실제 처리(사진 읽기+AI+저장)는 평균 3.0초.
- 변경: 제출 커밋 직후 전용 실행기로 판정 시작. 워커는 단계(차지·AI·저장)를 나누고 작업마다 짧은 트랜잭션으로 처리해 AI 대기 중 DB 연결·잠금을 잡지 않는다. 30초 워커는 안전망으로 유지.
- 검증: 신규 7건·백엔드 전체 325건 통과(건너뜀 1, R-46). 근거는 Decisions DEV-20261122-01. 운영 개선 후 측정은 배포 후 진행.

`PhotoRecoveryPolicy`는 T+30 이후에도 T 이전에 정상 접수된 동일 attempt만 `Evaluating` 상태에서 내부 복구할 수 있도록 한다. 새 사진 제출이나 완료·거절·기술실패·철회 attempt의 재처리는 허용하지 않는다.
