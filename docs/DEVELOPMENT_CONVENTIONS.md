# Dodu 개발 컨벤션

이 문서는 Dodu 저장소의 신규 개발·변경·리뷰 기준입니다. 제품 정책과 API/DB 확정 명세가 아닙니다.
사용자의 작업 범위와 [AGENTS.md](../AGENTS.md)를 함께 따르며, 제품 정책은 v2.5 원문이 우선합니다.
현재 자동 검사 도구와 아래 작성 규칙은 구분합니다. 규칙을 문서화했다고 자동 검사까지 적용된 것은 아닙니다.

## 작업 범위와 결정 처리

- 작업 전 구현 컨텍스트, OPEN_DECISIONS, 관련 원문과 수용 기준을 읽습니다.
- Notion 기준 페이지와 하위 항목을 매 작업 시작 시 다시 확인합니다. 접근 실패와 문서 충돌은 보고합니다.
- 확정 정책, 초기 운영값, 기술설계 제안, OPEN 결정을 구분합니다.
- OPEN 항목에 의존하는 사용자 동작은 구현하지 않습니다. 독립적인 기반 작업은 진행합니다.
- 결정 승인 시 ID·내용·담당·승인일·근거·정책 버전·영향 범위를 기록합니다.
- 원문 `docs/dodu/sources/`는 변경하지 않습니다. 합의된 변경은 별도 결정 기록과 파생 문서에 반영합니다.
- 미래 후보 기능을 미리 만들거나 포인트·손실·등급 등 제외 기능을 복원하지 않습니다.

## 저장소와 의존성

- Java는 `backend/`, React는 `frontend/`, 공통 명령은 루트 `package.json`과 `scripts/`에서 관리합니다.
- Node 의존성 설치는 루트 `npm ci`를 사용합니다. 루트 lockfile을 함께 커밋합니다.
- 프런트엔드 의존성 추가는 루트에서 `npm install <패키지> --workspace frontend`를 사용합니다.
- Java 의존성은 `backend/pom.xml`에서 관리하고 Maven Wrapper로 실행합니다.
- 새 라이브러리·DB·알림·AI·배포 도구는 현재 필요와 선택 이유를 기록한 뒤 도입합니다.
- 생성물·로컬 JDK·Maven 캐시·비밀값은 Git에 포함하지 않습니다.
- 개인 PC의 절대 경로를 공유 설정에 넣지 않습니다. 실행 경로는 프로젝트 루트나 환경변수를 사용합니다.

## 명명과 서식

| 대상 | 규칙 | 예시 |
|---|---|---|
| Java 패키지 | 소문자, 기능 이름 | `com.dodu.promise` |
| Java 클래스·인터페이스·record | PascalCase | `PromiseService`, `CreatePromiseRequest` |
| React 컴포넌트·타입 | PascalCase | `PromiseForm`, `PromiseDraft` |
| 컴포넌트 파일 | PascalCase `.tsx` | `PromiseForm.tsx` |
| 함수·변수·속성 | camelCase | `scheduledAt`, `handleSubmit` |
| 사용자 정의 React Hook | `use` 접두사 | `usePromiseDraft` |
| 상수 | UPPER_SNAKE_CASE | `POLICY_VERSION` |
| Java 테스트 | 대상 + `Tests` 또는 `Test` | `PromiseServiceTests` |
| 프런트엔드 테스트 | 대상 + `.test.ts(x)` | `PromiseForm.test.tsx` |
| CSS 클래스 | kebab-case | `promise-summary` |

- 신규 Java는 공백 4칸, TS/TSX·JSON·CSS는 공백 2칸을 사용합니다.
- TS/TSX는 작은따옴표와 세미콜론 생략, Java는 문법에 맞는 세미콜론을 사용합니다.
- UTF-8, 파일 끝 개행을 사용합니다. 기존 파일의 개행·서식을 무관하게 일괄 변경하지 않습니다.
- 기존 주석과 코드 변경 규칙을 보존합니다. AGENTS.md에 따라 교체하는 기존 코드는 문법에 맞게 주석 처리하고 새 코드를 추가합니다.
- 코드 식별자는 영어, 사용자 문구와 협업 설명은 명확한 한국어를 기본으로 합니다.
- import는 사용하지 않는 항목을 제거하고 관련 항목끼리 모읍니다. 변경한 기존 import도 보존 규칙을 따릅니다.
- 범용 이름 `data`, `manager`, `util`보다 역할이 드러나는 이름을 사용합니다.
- Formatter·Java 스타일 검사 도구는 아직 없습니다. 위 서식 규칙은 리뷰 기준입니다.

## Java 구조

새 기능은 `com.dodu.<기능>` 패키지 아래에서 관리합니다. 아래 구조는 기능이 필요할 때 적용하며 빈 계층을 미리 만들지 않습니다.

```text
com.dodu.promise
├── controller/     # HTTP 입력·응답 매핑
├── service/        # 사용 사례·트랜잭션·정책 적용
├── domain/         # 도메인 상태와 규칙
├── repository/     # 저장 접근: DB 도입 후
└── dto/            # 요청·응답 계약
```

- Controller에 업무 규칙·저장 처리를 넣지 않습니다. 의존성 주입은 생성자 주입을 사용합니다.
- DTO와 영속 객체를 분리합니다. API에서 Entity나 민감한 내부 필드를 직접 노출하지 않습니다.
- 단순 DTO는 Java record를 우선 검토합니다. 라이브러리·직렬화 요구와 맞지 않으면 일반 클래스를 사용합니다.
- 예상 가능한 입력 오류·충돌과 내부 기술오류를 구분합니다. 예외를 삼키거나 성공 응답으로 바꾸지 않습니다.
- 저장 트랜잭션은 사용 사례 경계에서 정의합니다. DB·마이그레이션 방식은 도입 시 별도 기술 기록을 남깁니다.
- 동시성 제약은 서버와 저장 계층에서 보장합니다. 프런트엔드 버튼 비활성화만으로 보장하지 않습니다.
- 시각에 의존하는 로직은 `Clock` 등 교체 가능한 시간 공급원을 사용해 경계 검증이 가능하게 설계합니다.

## React와 TypeScript 구조

기능이 늘어날 때 `src/features/<기능>/`에 컴포넌트·Hook·타입·API 호출을 모읍니다.
여러 기능이 실제로 공유하는 요소만 `src/components/`, `src/lib/` 등으로 분리합니다.

- 함수형 컴포넌트와 Hook을 사용합니다. 화면 렌더링, API 호출, 업무 데이터 변환의 책임을 구분합니다.
- 서버에서 받은 상태와 사용자가 작성 중인 입력 상태를 구분합니다. 파생값은 불필요하게 별도 상태로 저장하지 않습니다.
- 불필요한 `any`, 타입 단언, non-null assertion을 추가하지 않습니다. 외부 입력은 `unknown`에서 검증합니다.
- API JSON의 타입 단언만으로 런타임 응답 검증을 대신하지 않습니다.
- 요청은 상대 경로 `/api/...`를 사용합니다. localhost 주소를 화면 코드에 하드코딩하지 않습니다.
- 로딩·빈 결과·입력 오류·기술오류를 구분하고, 요청 취소·중복 클릭·늦은 응답이 이전 화면을 덮어쓰지 않게 합니다.
- 실제 저장하지 않은 입력을 저장 완료로 표시하지 않습니다. 미구현 기능은 수행한 것처럼 보이지 않게 합니다.
- 기본 HTML 요소, label, 키보드 접근, 포커스와 상태 안내를 우선 사용합니다.
- 알림·카메라 권한은 목적 안내와 사용자 동작에 맞춰 요청합니다. 권한 거부를 인증 거절·기술오류로 합산하지 않습니다.
- 현재 TypeScript 설정은 사용하지 않는 항목 등 일부 검사를 활성화했습니다. `strict` 전체는 활성화되지 않았습니다.
  strict 전환이나 새 테스트·UI 도구 도입은 별도 변경으로 다룹니다.

## API·시간·상태 계약

- 신규 API는 `/api` 아래에 두고 요청·응답·오류·권한·동시 요청 동작을 구현 전에 문서화합니다.
- 현재 API는 `GET /api/health`뿐입니다. 다음 규칙은 신규 API의 작성 기준이며 확정된 제품 API 명세는 아닙니다.
- 입력 오류는 400, 인증 없음은 401, 권한 부족은 403, 자원 없음은 404, 상태 충돌은 409 등 HTTP 의미에 맞춰 사용합니다.
- 오류에는 안전한 사용자 메시지와 구분 가능한 오류 코드를 제공합니다. 스택·접근정보·원문 사진 데이터는 응답에 넣지 않습니다.
- 참가자 접근 제어는 서버에서 수행합니다. 클라이언트가 전달한 참가자 ID만 신뢰하지 않습니다.
- 기술설계 기본 방향은 서버 시간·저장 상태를 최종 판단 기준으로 삼는 것입니다. 브라우저 타이머는 안내용입니다.
- 외부 시각은 UTC/오프셋이 포함된 ISO 8601로 전달하고, 사용자 표시와 일자 정책은 `Asia/Seoul`을 기준으로 변환합니다.
- 예약 끝점 비교·유효 서버 접수의 정의는 D11 승인 전 임의로 확정하지 않습니다.
- 예약 수정 이력, 판정 시도·이벤트 연결, 중복 제거·늦은 결과 처리 계약은 관련 D-ID를 표시합니다.
- 인증 종료 창과 판정 완료를 분리합니다. 마감 전 정상 접수된 유효 사진의 결과를 기다린다는 원문 원칙을 유지합니다.
- 인증 결과와 실제 시작, 권한 부재·기술 실패·취소·철회, 설문 응답 상태를 각각 구분합니다.
- 재진입·재알림은 인증 시간이나 세션을 새로 부여하지 않습니다.

## 로그와 데이터

- 관찰한 사실만 기록합니다. 알림 발송을 수신·열람으로, 인증 완료를 실제 시작으로 기록하지 않습니다.
- 이벤트명·필드·소유자·연결키·분모는 로그 매핑과 관련 OPEN 항목을 확인해 계약으로 정합니다.
- 사진·접근 토큰·참가자 식별정보·설문 원문을 콘솔, 예외, 디버그 로그에 남기지 않습니다.
- 철회 후 수집·개입·접근 중단과 늦은 비동기 결과 미반영을 지킵니다. 철회와 과거 데이터 삭제 요청은 구분합니다.
- 사진·원시 이벤트·개별 설문·식별 연결의 보관·삭제는 운영 정책 §11~13을 따릅니다.
- 테스트·문서 예시는 가상 데이터를 사용합니다. 비밀값은 저장소에 넣지 않습니다.

## 검증

- 코드 변경 시 기본 검증 명령은 루트 `npm run verify`입니다.
- 예약 시간 경계·동시 요청·상태 충돌·스케줄 수정·늦은 AI 결과·철회·데이터 연결처럼 실제 위험을 검증합니다.
- 단순 구현 복제 테스트나 문구·서식 수정만을 위한 테스트는 추가하지 않습니다.
- 승인되지 않은 OPEN 기대 결과를 테스트의 정답으로 고정하지 않습니다.
- 문서만 변경한 경우 링크·명령·파일 구조·정책 근거를 확인합니다. 불필요한 앱 테스트를 실행하지 않습니다.
- 수행한 검사와 미실행 검사를 구분합니다. 현재 프런트엔드 단위·브라우저 자동 테스트와 CI는 미구성입니다.
- 앱 테스트와 기기 QA·AI QA·행동검증을 구분해 보고합니다.

## Git과 PR

상세 절차와 리뷰·병합 기준은 [PR 컨벤션](PR_CONVENTIONS.md)을 따릅니다.
기본·개발 통합 브랜치는 `dev`, 배포용 브랜치는 `main`입니다. 작업 브랜치는 `dev`에서 분기하고 PR로 `dev`에 병합합니다. 배포 시에는 검증된 `dev`에서 `main`으로 배포 PR을 엽니다.
신규 작업 브랜치는 Jira 키를 포함합니다. 아래 `<주제>` 형식은 Jira 없는 작은 정리에 한해 사용합니다.

- 신규 브랜치는 `feat/<주제>`, `fix/<주제>`, `docs/<주제>`, `chore/<주제>` 형식을 사용합니다.
- 기본 브랜치 보호·필수 리뷰 수·병합 방식은 원격 저장소 구성 시 정합니다. 현재 적용됐다고 가정하지 않습니다.
- 커밋 제목은 `<type>: <변경 요약>` 형식입니다. 필요하면 `<type>(<범위>): <요약>`을 사용합니다.
- type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`를 사용합니다.
  예: `docs: 개발 컨벤션과 실행 안내 정리`.
- 하나의 커밋에는 검토 가능한 하나의 목적을 담습니다. 관련 lockfile·계약 문서도 함께 반영합니다.
- 매 커밋마다 [Decisions.md](../Decisions.md)에 배경·결정·근거·검토한 대안·영향·검증을 기록하고 같은 커밋에 포함합니다. 문서·설정 변경도 예외가 아닙니다.
- 영문 `<type>: <summary>` 제목 뒤 빈 줄과 영문 변경 사항 목록을 작성하는 형식을 허용합니다. `Co-authored-by` 등 공동 작성자 표기는 추가하지 않습니다.
- `.tools/`, `node_modules/`, `target/`, `dist/`, 로그·비밀값은 커밋하지 않습니다.
- 생성된 Maven Wrapper 파일은 재현 가능한 빌드를 위해 포함합니다.
- PR은 문제와 변경 후 동작을 먼저 설명하고, 영향·검증·정책 근거·남은 D-ID를 적습니다.
- PR 본문에는 다음 항목을 사용하되 간단한 변경은 짧게 작성합니다.

```markdown
## 변경 내용
문제와 변경 후 동작, 주요 영향.

## 검증
실행한 명령과 결과, 미실행 검증과 이유.

## 정책·미결정 사항
근거 문서/절, 관련 D-ID, 보류한 동작 또는 해당 없음.
```

## 문서 유지

- 실행·의존성·구현 범위가 바뀌면 루트 README를 함께 갱신합니다.
- 내부 링크는 저장소 상대 경로를 사용합니다. 개인 경로·가상의 원격 주소를 넣지 않습니다.
- 도구가 생성한 Vite/Maven 안내 문서와 Dodu 루트 README를 구분합니다.
- 이 컨벤션의 도구·서식 변경은 변경 이유를 기록하고 기존 코드 일괄 수정과 분리합니다.
