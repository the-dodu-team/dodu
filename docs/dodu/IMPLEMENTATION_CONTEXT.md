# Dodu v2.5 구현 컨텍스트

상태: 2026-09-27 Notion LOCKED 결정문(D01~D13)을 반영한 파생 요약 + 명시적으로 구분한 기술설계 제안. 원문 우선.

## 제품과 Sprint 범위
- 대상: 할 일과 시작 방법을 알고도 혼자 하는 개인작업의 계획한 시작을 반복해서 넘기는 성인.
- 검증: 약속한 시점의 행동 요구 → 작업환경 인증 → 자기보고 실제 시작의 연결 가능성.
- 컴퓨터·책 사진은 준비 행동에 대한 응답이며 실제 작업 시작 증명이 아니다.
- 플랫폼: 웹앱/PWA. 폐쇄형 참가자 식별; 정식 회원가입·소셜 로그인 제외.
- Sprint 1: 정책·흐름·기술 구조·디자인 착수·개발환경·핵심 기반. 전체 MVP 완성/실서비스 배포를 완료 기준으로 가정하지 않는다.
- 제외: 포인트, 손실, 등급, streak, 배지, 캐릭터, 랭킹, 사회적 비교, 화폐 손실, OS 앱 차단, 작업 타이머·완료·지속시간 분석.

## 상태 모델 — 원문 요약
약속: Draft, Scheduled, AuthAvailable, Evaluating, TechError, AuthCompleted, AuthIncomplete, Cancelled, TechFailed, PermissionBlocked, Withdrawn, Closed.
자기보고: NotEligible, Pending, Prompted, InAppReprompted, Submitted, Skipped, Expired.
상태명은 구현팀이 API/DB 계약에서 구체화하되, 정상 미완료와 기술·권한·취소·철회를 합치지 않는다.

## 기술설계 제안 — 승인된 API/DB 명세 아님
- 논리 데이터 모델과 D01~D13 적용 범위는 [DATA_MODEL.md](DATA_MODEL.md)를 참조한다.
- 약속의 진행 상태와 최종 종료 사유를 분리해 Closed 이후에도 결과를 보존한다.
- 서버의 접수시각과 상태를 최종 판단 기준으로 사용하고 FE 타이머는 안내에 사용한다.
- promise_id 아래 변경 이력, attempt_id 아래 제출·판정·오류를 연결한다.
- event_id, 서버 접수시각, 판정 완료시각, 스케줄 버전, 정책 버전, 모델 버전, 분석 제외 사유를 검토한다.
- 스케줄 실행 직전에 취소·성공·철회·시간 수정 여부를 재확인한다. 수정 전 예약 작업과 중복 실행에 안전하게 설계한다.
- 사진 제출은 약속/attempt/event 단위로 분리하고, 네트워크 retry는 같은 attempt로 멱등 처리한다. Evaluating 중 추가 제출과 T+10/T+20 재알림은 막는다.
- 알림 발송·사용자 진입·인증 제출·최종 결과를 별도 사건으로 기록한다. 수신/열람은 관찰 가능할 때만 기록한다.
- 참가자 코드는 여러 기기에서 재사용할 수 있지만 활성 세션은 참가자당 하나만 유지한다. 같은 기기 재진입은 불투명 기기 식별 상태를 복원하고, 새 기기 진입은 기존 세션과 기존 알림 구독을 종료한 뒤 새 세션·구독을 활성화한다.
- 약속·인증·자기보고·행동로그는 세션/기기 ID가 아닌 `participant_id`에 귀속한다. 코드 분실·노출 시 기존 접근 자격을 폐기하고 교체 자격을 발급한다.
- 앱 진입·온보딩·권한·이력 조회처럼 약속 이전/외부 사건은 promise_id가 없을 수 있다. 모든 사건에 가짜 약속 ID를 만들지 않는다.
- 정책·모델 변경 전후의 결과를 무조건 합산하지 않는다. D13의 Go/부분 Go/판단 보류/No-go는 로그·자기보고·인터뷰를 함께 보고 기술·AI QA 기록과 분리한다.

## 역할 및 착수 순서 — 제안
| 작업 | 주도 및 협업 | 산출물 |
|---|---|---|
| 최종 결정 반영 | PO + PD + 개발 | D01~D13 승인 기록과 동기화된 계약 |
| UX/프로토타입 | PD + FE | 정상·거절·권한·기술오류·마감·설문 화면 |
| 저장소/환경 조사 | FE + BE/FS | 실제 스택 및 실행 절차 |
| 상태·시간·스케줄 | BE/FS + FE | 전이표·API 계약·경계 처리 |
| 사진 판정 | AI + BE/FS + FE | 입력/출력·timeout·QA·모델 버전 |
| 로그·분석 | BE/FS + FE + PO | 사건 소유자·연결키·분모·제외 기준 |

UI/환경 기반은 병렬 착수 가능하다. 기술 담당 구분은 팀 합의로 확정한다. 기존 저장소 확인 없이 새 프레임워크/DB/알림 업체를 선택하지 않는다.

## 측정의 한계
- 전체 개입 흐름의 가능성 관찰이며 사진 인증만의 인과 효과를 증명하지 않는다.
- 자기보고 미응답, 권한 부재, 기술 실패를 분리해 보고한다.
- 행동 지표와 함께 전체 약속 기준 기술 실패/제외 비중을 보고한다.
- Go/부분 Go/No-go의 최소 관찰량과 판단 보류 기준은 별도 행동검증 운영안에서 정한다. 해당 운영안은 첨부되지 않았다.
