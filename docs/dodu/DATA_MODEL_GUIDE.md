# ERD 설명서

이 문서는 [논리 ERD](DATA_MODEL.md)의 관계를 문장으로 풀어 검토하기 위한 설명서입니다.
그림과 설명이 다르면 문장만 다듬지 않고 필드·관계·제약을 함께 수정합니다.
2026-09-22 기준이며 DB 제품, JPA 엔티티, 마이그레이션은 아직 만들지 않았습니다.

## 읽는 방법과 구현 범위

테이블은 같은 종류의 사실을 모으고, 행 하나는 아래 표의 단위를 뜻합니다.
PK는 행을 구분하는 키, FK는 다른 행을 참조하는 키, UK는 중복을 금지하는 키입니다.
Mermaid의 `||`는 정확히 하나, `|o` 또는 `o|`는 없거나 하나, `o{`는 없거나 여러 개입니다.
예를 들어 참가자 한 명에게 약속은 여러 개 생길 수 있지만, 약속 하나의 소유자는 항상 한 명입니다.

그림의 uuid·timestamp·json은 개념 타입입니다. UUID 생성 방식, SQL 타입, 길이,
인덱스, 암호화와 DB 공급자는 DODU-19·21에서 선택합니다. timestamp는 시간대가 모호한
문자열이 아니라 UTC 순간을 뜻하고, 날짜별 제한에는 Asia/Seoul 변환을 적용합니다.

이 ERD 전체는 구현 승인이 아닌 검토 후보입니다. 참가자 접근 방식과 저장 기반부터 검토하고,
예약 경계(D06/D11), 인증·이벤트(D04/D05/D08/D10), 설문(D01/D02/D03/D07/D12)에
의존하는 동작은 결정 승인 전 구현에서 제외합니다. 그림에 후보 필드가 있다는 이유로 기본값을 정하지 않습니다.

## 행 하나에 무엇을 저장하는가

| 엔티티 | 한 행의 의미 | 그렇게 나누는 이유와 근거 |
|---|---|---|
| `STUDY_PERIOD` | 행동검증 운영 기간 하나 | 보관 기산점인 공식 종료와 서비스별 종료 경계를 구분합니다. 정책 §11~13, D03 |
| `POLICY_VERSION` | 적용 가능한 운영 조건의 변경 불가능한 스냅샷 하나 | 버전 이름만 남기고 설정을 덮어쓰면 과거 조건을 재현하지 못합니다. 정책 §0·16 |
| `PARTICIPANT` | 해당 검증 기간에 참여하는 참가자 하나 | 회원가입·소셜 계정 없이 데이터를 소유하는 주체입니다. 여러 기간 재참여 모델은 현재 범위 밖입니다. 정책 §12 |
| `ACCESS_CREDENTIAL` | 발급된 접근 자격 하나 | 참가자와 비밀정보를 나누어 재발급해도 업무 데이터 소유자는 유지합니다. 정책 §12 |
| `PARTICIPANT_PERMISSION` | 특정 클라이언트에서 관찰한 권한 상태 하나 | 기기마다 상태가 다를 수 있어 참가자 전체의 영구적인 권한으로 단정하지 않습니다. 정책 §7 |
| `PROMISE` | 저장된 시작 약속 하나 | 작업명·도구·현재 예정 시각·인증 결과를 묶습니다. 작성 중인 Draft의 서버 저장은 요구하지 않습니다. PRD F-01 |
| `PROMISE_SCHEDULE_REVISION` | 약속 시작시간 수정 하나 | 약속 ID를 새로 만들지 않고 이전·새 시각을 보존합니다. 정책 §2, Flow §3 |
| `AUTH_ATTEMPT` | 서버가 기록한 사진 제출 요청 하나 | 재촬영은 서버 제출 전까지 행을 만들지 않습니다. 거절 후 새 제출과 통신 재전송을 구분합니다. 정책 §5, D08/D10 |
| `PHOTO_ASSET` | 시도에 연결된 사진 저장 참조 하나 | 업로드 실패나 보관 만료 후에는 없을 수 있습니다. 사진 없는 시도를 인증 성공으로 처리하지 않습니다. 정책 §11 |
| `NOTIFICATION_DELIVERY` | 특정 약속·일정 세대·알림 종류의 논리 발송 작업 하나 | 시작·첫 재알림·둘째 재알림·설문 리마인드를 구분합니다. 재시도는 같은 논리 작업을 사용합니다. 정책 §3·10 |
| `VALIDATION_SURVEY` | 대상 약속 하나에 대한 자기보고 슬롯과 응답 | 약속은 설문이 없거나 하나 있고, 설문 행은 반드시 약속 하나에 속합니다. 생성 대상은 D12 승인 대기입니다. 정책 §10 |
| `BEHAVIOR_EVENT` | 중복 제거 가능한 관찰 사실 하나 | 진입·제출·판정을 별도 사건으로 기록합니다. 시스템 사실과 자기보고를 혼합하지 않습니다. Flow §3~7 |
| `DATA_REQUEST` | 철회 또는 과거 데이터 삭제 처리 요청 하나 | 철회는 수집 중단, 삭제는 기존 자료 제거이므로 완료 조건이 다릅니다. 정책 §13 |

## 관계를 문장으로 확인하기

1. 참가자는 검증 기간 하나에 속합니다. 기간에는 참가자가 아직 없을 수 있습니다.
2. 참가자에게 여러 약속이 있어도 동시에 활성인 약속은 하나뿐입니다. 1:N 그림만으로 활성 제한을 보장하지 않으므로 저장 트랜잭션과 제약이 필요합니다.
3. 약속 하나는 생성 시점의 정책 버전 하나를 참조합니다. 이후 스냅샷 내용을 덮어쓰지 않고 새 버전을 만듭니다.
4. 약속은 시간 수정 이력이 없거나 여러 행일 수 있습니다. 현재 정책의 정규 수정 최대 1회는 서비스 검증으로 제한합니다. 이력 1:N이 무제한 수정을 허용한다는 뜻은 아닙니다.
5. 시도에는 사진 메타데이터가 없거나 하나 있습니다. 사진 메타데이터가 있으면 그 소유 시도는 반드시 하나입니다. 30일 보관 종료로 사진을 삭제해도 90일 한도 내 시도의 비사진 사실은 남을 수 있습니다.
6. 이벤트에는 참가자가 반드시 있습니다. 온보딩 사건은 약속과 시도가 모두 NULL이며, 약속 생성 사건은 약속만, 사진 판정 사건은 약속과 시도를 함께 가집니다.
7. 참가자의 삭제 요청은 처리 중 참가자를 참조합니다. 완전 삭제가 끝나면 그 FK도 제거하므로 완료된 요청은 참가자와 연결되지 않을 수 있습니다.
8. 재발급된 접근 자격은 이전 자격을 참조할 수 있습니다. 최초 발급에는 이전 자격이 없으며 이전 자격을 두 번 대체하거나 다른 참가자의 자격과 연결하지 않습니다.

## 필드와 제약을 해석할 때의 주의점

### 운영 기간과 참가자

`official_ends_at`은 사진 30일·원시 데이터 90일 보관의 공식 기산점입니다.
`photo_delete_after`와 `raw_data_delete_after`는 그 최대 한도를 넘지 않는 삭제 기한입니다.
기산점의 운영 확정 전에는 임의 날짜를 채우지 않습니다. 다른 종료 후보 필드도 D03 승인 전 NULL로 두는 설계입니다.
특히 설문 회수 끝점과 접근 끝점의 선후관계를 현재 문서만으로 결정하지 않습니다.

`public_code`는 참가자 내부 업무용 가명 코드이며 이름과 달리 외부 공개 허가를 뜻하지 않습니다.
단독 인증 수단으로 쓰지 않습니다. `onboarding_completed_at`은 완료 사실을 기록할 수 있는 nullable 시각입니다.
`withdrawn_at`과 `access_disabled_at`은 철회와 접근 종료를 구분합니다. 기술적 상태값의 최종 목록은 D05 계약에서 정합니다.

접근 비밀값은 `secret_hash`로 검증하고 원문을 저장하지 않는 기술안을 제안합니다.
발급 방식·엔트로피·해시 알고리즘은 아직 미정입니다. 재발급은 기존 자격 폐기와 새 자격 발급을 하나의 트랜잭션으로 처리하며,
별도 세션을 도입하면 기존 세션 무효화도 설계해야 합니다. `replaces_credential_id`는 nullable FK+UK입니다.

권한 행의 `client_context_id`는 개인정보를 포함하지 않는 불투명한 클라이언트 문맥 키입니다.
`observed_at`은 클라이언트 관찰 시각, `received_at`은 서버 수신 시각입니다.
권한 이력이 있다는 사실만으로 현재 기기의 알림·카메라 사용 가능성을 보장하지 않습니다.

### 약속과 일정 변경

`task_title`은 PRD F-01의 작업명입니다. 임의 길이 제한을 제품 정책으로 추가하지 않으며 실제 길이·입력 검증은 API 계약에서 정합니다.
`scheduled_date_kst`는 `scheduled_at`을 KST로 변환한 날짜와 같아야 하고 별도로 임의 수정하지 않습니다.
`schedule_version`은 시간 수정 시에만 증가하여 이전 알림을 식별합니다.
`row_version`은 결과·취소 등 모든 상태 변경의 동시성 충돌을 막는 별도 버전입니다.

이력의 유일성은 version 하나가 아니라 `(promise_id, version)`입니다.
다른 약속 두 개에 각각 첫 수정 이력인 version=1이 있어도 충돌하지 않습니다.
취소 후 당일 생성 제한은 유지합니다. 날짜 이동 후 이전 날짜를 다시 쓸 수 있는지와 기술 실패 후 당일 재예약은 D06이므로,
현재 예정일의 유일 인덱스 하나로 모든 날짜 제한을 해결했다고 간주하지 않습니다. 날짜 사용 원장 채택 여부도 승인 이후 검토합니다.

`lifecycle_status`는 진행 단계, `final_outcome`은 종료 결과입니다. 종료 사유를 Closed 하나로 덮어쓰지 않습니다.
`auth_completed_at`은 인증 성공 확정 시각이고 `closed_at`은 개입 종료 시각이므로 서로 대체하지 않습니다.
두 값은 미발생 시 NULL입니다. 인증 완료 시각을 실제 작업 시작 시각으로 사용하지 않습니다.

### 제출·사진·알림

시도의 `request_received_at`은 요청 도착 시각이고 `valid_received_at`은 정상 유효 제출의 접수를 확정한 시각입니다.
후자는 유효 제출이 아닐 때 NULL입니다. 어떤 검사를 마쳐야 유효한지, 정확히 마감과 같은 시각을 허용할지는 D11 승인 대상입니다.
`decided_at`과 판정값은 아직 결과가 없으면 NULL입니다. 기술오류를 판정거절로 저장하지 않습니다.

`(promise_id, client_request_id)`는 재전송을 찾는 복합 유일 키입니다.
`request_fingerprint`는 같은 키로 다른 파일·입력이 제출되는지 비교하기 위한 값입니다.
두 요청의 저장을 먼저 하고 뒤에서 중복을 제거하지 않도록 원자적 삽입과 충돌 처리가 필요합니다.
동시에 여러 새 사진을 제출했을 때 어느 결과를 적용할지는 D10이며 이 키가 그 정책을 대신하지 않습니다.

사진은 `auth_attempt_id`에 FK+UK를 걸어 시도당 최대 한 행으로 제한합니다.
`deletion_status`와 안전한 오류 코드는 삭제 대기·실패 재시도에 사용합니다.
실제 파일 삭제와 관련 키 제거를 확인하면 사진 행 자체를 삭제합니다. `deleted_at`만 채우고 연결 키를 영구 보관하는 방식은 사용하지 않습니다.

알림의 `dispatch_key`는 약속 ID·일정 세대·종류를 구별하는 내부 유일 키입니다.
종류는 시작, 첫 재알림, 둘째 재알림, 설문 리마인드를 구분할 수 있어야 합니다.
`provider_message_id`와 `sent_at`은 공급자 응답 전에는 NULL입니다.
실행 직전에 철회·접근·일정 버전·이미 완료된 인증·설문 응답을 재검사합니다.
내부 키만으로 외부 공급자의 정확히 한 번 발송까지 보장할 수는 없습니다.
발송 성공 후 DB 저장이 실패하는 경우의 공급자 멱등성·조회·재시도 전략은 DODU-23 기술 검토에서 정합니다.
전송 구독 정보와 푸시 공급자별 테이블도 같은 작업에서 결정하므로 현재 그림에 임의 필드를 추가하지 않았습니다.

### 설문·이벤트·삭제 요청

설문의 `promise_id`는 FK+UK로 약속당 하나를 보장합니다. `questionnaire_version`은 실제 승인된 문항 버전을 가리킵니다.
`actual_started`는 미응답이면 NULL이고 명시적인 ‘아니오’만 false입니다.
시간 구간·미시작 이유·제출 시각은 응답 전 NULL입니다. 문항의 최종 값과 분기 제약은 D01 승인 후 확정합니다.
`available_at`·`expires_at`과 리마인드 시각은 D02/D07 결정 후 계산합니다. 설문 상태를 근거로 새 약속 생성을 막지 않습니다.

이벤트의 PK `event_id`는 같은 사건 재전송에서 유지해야 합니다. 재전송마다 새 ID를 발급하면 중복 제거가 불가능합니다.
시도 ID가 있으면 약속 ID도 있어야 하고, 해당 시도·약속·참가자의 소유 관계가 일치해야 합니다.
복합 FK 또는 트랜잭션 검증 방식은 DB 선택 이후 결정합니다.
`attributes`는 허용된 필드만 기록하며 사진 원문·접근 토큰·작업명·설문 원문을 복제하는 공간으로 쓰지 않습니다.
`policy_version`은 사건에 해당할 때만 기록하고 약속 사건에서는 약속의 버전과 일치시킵니다. 최종 이벤트 계약은 D08입니다.

일반 작업에서 이벤트를 수정하지 않는다는 규칙은 삭제 금지가 아닙니다.
삭제 요청이나 보관 종료 때 이벤트도 지워야 합니다. 참가자 FK만 NULL로 바꿔도 다른 필드에서 재식별 가능하면 삭제 완료가 아닙니다.
`DATA_REQUEST.last_error_code`는 실패의 안전한 분류 코드이며 스택·입력 원문을 저장하지 않습니다.
완료 요청 행의 보존 기간은 아직 확정하지 않았고, 완료 전에 `purge_after` 운영 기준을 정해야 합니다.

## 생성부터 삭제까지 따라가기

다음은 데이터 이동을 점검하는 가상 시나리오입니다. OPEN 항목의 기대 결과를 확정하는 테스트가 아닙니다.

1. **참여 준비:** 기간과 정책 버전을 확인하고 참가자 P를 만듭니다. 접근 자격 C를 발급하며 온보딩 완료와 기기 권한 관찰을 각각 기록합니다.
2. **약속 저장:** P가 작업명·도구·예정 시각을 입력해 약속 A를 만듭니다. 활성 제한과 승인된 시간·날짜 조건을 같은 트랜잭션에서 확인합니다.
3. **시간 수정:** A의 첫 수정 이력 `(A, 1)`을 기록하고 일정 세대와 행 버전을 갱신합니다. 예전 세대의 알림은 새 약속 상태를 바꾸지 못합니다.
4. **사진 제출:** 시도 R을 만듭니다. 업로드 실패면 사진 행과 유효 접수 시각이 없을 수 있습니다. 유효 제출이면 사진 참조와 접수 사실을 기록하고 판정을 기다립니다.
5. **판정·자기보고:** 승인된 전이에 따라 인증 결과를 기록합니다. 설문 대상·노출 조건이 충족되면 S를 만들고 응답은 인증과 독립적으로 저장합니다.
6. **철회:** 접근·신규 수집·예약 개입을 중단합니다. 이미 처리 중인 콜백은 요청 존재만 보고 반영하지 않고 철회 여부를 다시 확인합니다. 과거 데이터는 삭제 요청 없이는 원래 보관 한도를 따릅니다.
7. **완전 삭제:** 삭제 작업이 재생성을 막고, 사진·파생본을 먼저 찾아 제거합니다. 이후 사진 참조·설문·이벤트·알림·시도·일정 이력·약속·권한 이력·자격을 정리합니다. 재발급 자격의 자기참조를 해제하고 모든 관련 요청의 참가자 FK를 제거한 뒤 참가자를 삭제합니다.

완전 삭제는 인증 자격 행 하나를 지우는 것으로 끝나지 않습니다. 작업명·로그·외부 공급자 데이터·백업도
재연결 경로인지 확인해야 합니다. 백업을 도입할 때는 보존 기간과 복원 후 삭제 재적용 절차를 같이 정합니다.
사진 삭제가 실패한 상태에서는 참가자 연결을 먼저 지워 재시도 대상을 잃지 않도록 합니다.
삭제 처리 자체의 최소 운영 기록과 새로운 행동 데이터 수집은 구별하며, 원시 행동을 계속 수집하지 않습니다.

## 설명 검토로 수정한 ERD

| 설명 중 발견한 문제 | 그림·제약 수정 |
|---|---|
| “약속에 작업명이 있다”를 설명할 필드가 없었음 | `PROMISE.task_title` 추가 |
| “온보딩 이벤트에는 약속이 없다”와 필수 약속 관계가 충돌 | 이벤트의 약속·시도 관계를 선택 관계로 수정 |
| 업로드 실패·보관 종료 후에도 사진이 반드시 하나라고 표시됨 | 시도에서 사진을 0..1로 수정하고 사진 FK에 UK 추가 |
| 약속 두 개의 첫 수정 이력이 각각 version=1을 가질 수 없었음 | version 단독 UK 제거, 복합 유일성 명시 |
| 일정 세대만으로 취소·판정 동시 갱신을 설명할 수 없었음 | 별도 `row_version` 추가 |
| “설문 미응답”이 false와 구분되지 않을 수 있었음 | 응답 NULL 규칙과 문항 버전, 약속 FK+UK 명시 |
| 공식 종료와 설문 회수 끝점이 불명확했음 | 공식 종료·설문 회수·사진 삭제 끝점 추가, D03 값 확정은 보류 |
| 이벤트는 삭제 불가, 사진은 키를 계속 보존하는 것으로 읽혔음 | 이벤트 삭제 예외와 사진 메타데이터 제거 흐름 명시 |
| 삭제 완료 요청이 참가자 삭제를 막을 수 있었음 | 요청의 참가자 관계를 선택 관계로 바꾸고 완료 후 연결 제거·정리 기한 명시 |
| 공급자 메시지 ID만으로 중복 발송 방지를 설명했음 | 내부 `dispatch_key`와 외부 멱등성의 한계를 분리 |

## 검토 완료 기준

- 그림의 관계를 위 문장으로 읽어도 필수·선택 개수가 바뀌지 않습니다.
- 각 1:1 관계에 UK, 각 복합 유일성에 실제 컬럼 묶음이 있습니다.
- NULL이 미발생·미응답·해당 없음 중 무엇을 뜻하는지 설명할 수 있습니다.
- 다른 참가자의 FK를 섞어 저장할 수 없도록 소유 관계 검증 지점이 있습니다.
- 보관 만료와 삭제 요청이 파일뿐 아니라 연결 키까지 제거합니다.
- OPEN 결정의 필드 후보와 바로 구현 가능한 범위를 혼동하지 않습니다.

구현 전 검토자는 문은서와 mono이며, 설문·API 표현은 Elle Yoo가 함께 확인하는 안입니다.
문서 검토가 끝났다는 사실은 제품 정책 승인이나 실제 DB 동작 검증을 뜻하지 않습니다.
