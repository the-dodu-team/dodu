# Dodu 구현 진행 순서 및 논의 질문

작성일: 2026-10-25

이 문서는 현재 저장소와 승인된 파생 문서를 기준으로, 추가 정보 없이 진행할 수 있는 작업과 외부 결정이 필요한 작업을 분리한다. 원문 `docs/dodu/sources/`는 변경하지 않는다.

## 1. 추가 정보 없이 진행할 순서

| 순서 | 작업 | 담당 | 필수 검증 | 현재 상태 |
|---|---|---|---|---|
| 1 | 공식 개입 종료 이후 신규 개입성 알림 스케줄러 차단 | 강민 | 알림 스케줄러 기능 테스트, 멱등성 테스트 | 진행 |
| 2 | 알림·사진·자기보고 상태 전이의 현재 attempt/철회/종료 경계 통합 테스트 보강 | 강민 | PostgreSQL/Testcontainers 기능 테스트 | 대기 |
| 3 | 약속 생성·수정·취소의 동시성·멱등성 실패 경로 테스트 보강 | 강민 | DB 제약조건 및 HTTP 기능 테스트 | 대기 |
| 4 | 인증 이력·자기보고·알림 조회 API의 소유권·민감정보 비노출 테스트 보강 | 강민 | MockMvc와 DB 기능 테스트 | 대기 |
| 5 | 공통 검증 명령과 파생 문서·Jira 상태 동기화 | 강민 | `npm run verify`, `git diff --check` | 반복 |

위 순서의 작업은 현재 정책과 저장소 구조만으로 구현할 수 있다. 단, 외부 제공자 계약이 필요한 항목은 아래 AI 차단 목록으로 이동하며 완료로 표시하지 않는다.

## 2. AI 관련 분리 작업

다음 항목은 김경제(AI 담당자)의 계약 또는 운영 정보가 없으면 실제 구현을 확정할 수 없다.

- AI worker endpoint 또는 큐 연결 방식과 인증 방식
- 사진 저장소의 객체 참조 전달 방식 및 worker가 읽을 수 있는 권한 범위
- 요청 payload와 결과 callback/webhook payload의 필드·버전·서명 규칙
- 판정 결과의 허용값(`Completed`, `Rejected`, 기술 실패)과 거절 사유 코드 목록
- timeout, 재시도, 중복 callback, 지연 callback의 책임 주체
- 모델 버전·판정 시각·분석 예외 사유의 저장 계약
- AI 처리 실패와 사용자 정책상 거절을 구분하는 운영 기준
- 실제 provider를 이용한 재시작·중복 작업·철회 후 결과 QA 환경

현재 코드에는 provider 경계와 안전한 미설정 기본 동작만 있으며, 위 정보가 정해지기 전에는 실제 AI 연동 완료 또는 Jira 완료 처리를 하지 않는다.

### AI 담당자에게 전달할 질문

1. AI worker는 어떤 endpoint/queue를 사용하며 인증은 어떤 방식(API key, service token, mTLS 등)인가요?
2. worker에 전달할 사진 식별자는 어떤 객체 저장소 URI와 권한 모델을 사용하나요? 원본 사진 바이트를 API로 전달해도 되나요?
3. 요청과 결과의 JSON schema, schema/model version, idempotency key, callback 서명 필드를 제공해 주세요.
4. 결과 상태와 거절 사유 코드의 확정 목록은 무엇인가요? 기술 실패와 사용자 사진 거절을 어떻게 구분하나요?
5. timeout·재시도·중복 결과·지연 결과 중 어느 계층이 책임지며, worker는 동일 attempt를 몇 번까지 처리하나요?
6. 실제 연동용 개발/QA endpoint와 테스트용 결과 fixture를 제공할 수 있나요?

## 3. 팀 논의 후 진행할 작업

다음 항목은 구현자가 임의로 고정하면 FE·BE·운영 결과가 달라질 수 있으므로 팀 합의가 필요하다.

- 공통 API 응답 envelope와 오류 코드 표준
- Push 발송 provider 선정, Web Push endpoint/암호화 키 보관 방식, 발송 실패 재시도 책임
- 공식 개입 종료 후 알림의 정확한 범위와 자기보고 리마인드 허용 범위
- 신뢰 프록시 환경에서 원본 IP를 판별하는 배포 설정과 다중 노드 rate limit 저장소
- 실제 운영 QA의 담당자·환경·완료 증거와 Jira 완료 승인자
- 사진 객체 저장소의 보관·삭제·접근 로그 정책
- 인증 이력 API와 FE 화면의 최종 필드, 빈 상태, 로딩·오류 상태

### 팀에 확인할 질문

1. 공통 응답 envelope와 오류 코드의 최종 표준 문서를 어느 문서로 확정할까요?
2. Push provider와 운영 자격정보를 누가 발급·보관·교체하며, 발송 실패 재시도는 애플리케이션과 provider 중 어디가 담당하나요?
3. 공식 개입 종료 후에도 자기보고 24시간 리마인드 알림을 발송할까요? 발송한다면 종료 후 최대 시점을 정할까요?
4. 운영 환경의 trusted proxy 목록과 원본 IP 헤더 규칙은 무엇인가요?
5. Sprint 3의 최종 QA 실행자와 Jira 완료 승인자는 누구인가요?
6. 사진 저장소 보관·삭제 실행 결과를 이번 Sprint의 완료 조건으로 포함할까요?

## 4. 완료 기준

- 추가 정보 없이 가능한 작업은 코드·단위 테스트·기능 테스트를 함께 커밋한다.
- 외부 계약이 필요한 작업은 질문과 차단 사유를 기록하고 완료 처리하지 않는다.
- 각 커밋 전 `Decisions.md`를 갱신하고, 검증 결과를 `docs/jira/IMPLEMENTATION_STATUS.md`에 기록한다.
- Jira 상태는 실제 구현·검증 범위와 일치시킨다.
