## 0.1 정책값 상태

본 문서의 수치는 모두 설명 가능해야 하지만, 모두 사용자 리서치에서 검증된 최적값을 의미하지 않는다.

| 상태 | 의미 |
|---|---|
| 확정 정책 | 현재 MVP에서 의도적으로 선택한 운영 규칙 |
| 초기 운영값 | 최적값이 검증되지는 않았으나 일관된 행동검증을 위해 우선 고정하는 값 |
| 기술 기준 | 서비스 안정성·보안·데이터 관리 목적의 요구조건 |
| UT/QA 조정 가능 | 행동검증 시작 전까지 실제 사용성·기술 결과에 따라 수정 가능 |

행동검증 시작 이후 수치를 변경해야 할 정도의 문제가 발생한 경우, 기존 참가자와 신규 참가자의 조건을 동일 데이터로 단순 합산하지 않는다.

# 1. 작업 약속 생성 정책

## 1.1 예약 가능 범위

| 항목 | 정책값 | 상태 |
|---|---:|---|
| 최소 예약 가능 시점 | 현재 시각 + 30분 | 초기 운영값 |
| 최대 예약 가능 범위 | 현재 시각 + 72시간 | 초기 운영값 |
| 행동검증 종료일 이후 예약 | 불가 | 확정 정책 |
| 동시 활성 약속 수 | 사용자당 최대 1개 | 확정 정책 |
| 행동검증 기간 일일 약속 수 | KST 기준 동일한 예정 시작일에 사용자당 최대 1개 | 확정 정책 |

### 선택 이유

- `+30분`은 즉시 실행과 미리 계획한 시작 약속을 구분하면서도 당일 사용을 막지 않기 위한 초기값이다.
- `+72시간`은 당일·다음날·모레 수준의 실제 계획을 허용하면서, 1~2주 행동검증 안에서 반복 사용 데이터를 확보하기 위한 초기값이다.
- 행동검증 종료 이후의 예약을 허용하면 실제 검증이 불가능한 약속이 생성되므로 차단한다.
- 활성 약속을 1개로 제한하면 알림·인증·상태 복구·로그 귀속을 명확하게 유지할 수 있다.
- 행동검증 기간에는 KST 기준 동일한 예정 시작일에 약속 1개만 허용해 시스템 로그와 다음날 자기보고를 1:1로 연결한다.

> `30분 / 72시간`은 사용자 조사에서 최적값으로 확인된 수치가 아니다. 디자인 UT 및 행동검증에서 예약 불편, 수정 빈도, 실제 예약 분포를 확인한 뒤 후속 버전에서 조정한다.

### 처리 규칙

- 과거 시간은 선택할 수 없다.
- 현재 시각 +30분보다 이른 시간은 저장할 수 없다.
- 현재 시각 +72시간을 초과한 시간은 저장할 수 없다.
- 행동검증 공식 종료시각 이후의 약속은 저장할 수 없다.
- 활성 약속이 존재하는 동안 새 활성 약속을 동시에 생성할 수 없다.
- 선택한 예정 시작일(KST)에 이미 시작 약속이 1개 존재한다면 해당 예정 시작일의 추가 약속을 생성할 수 없다.
- 기존 약속이 취소되더라도 해당 날짜의 약속 생성 횟수는 복구하지 않는다.
- 기존 약속이 인증 완료, 인증 미완료, 취소 또는 기술 실패 종료 상태가 되면 다른 날짜의 새 약속을 생성할 수 있다.

# 2. 시작시간 수정·취소 정책

| 항목 | 정책 | 상태 |
|---|---|---|
| 시작시간 수정 가능 구간 | 약속 생성 후 ~ 시작시간 도달 전 | 확정 정책 |
| 정규 수정 횟수 | 약속당 최대 1회 | 초기 운영값 |
| 취소 가능 구간 | 약속 생성 후 ~ 시작시간 도달 전 | 확정 정책 |
| 시작시간 도달 이후 수정 | 불가 | 확정 정책 |
| 시작시간 도달 이후 취소 | 불가 | 확정 정책 |
| 별도 잠금구간 | 사용하지 않음 | 확정 정책 |
| 긴급 시간조정권 | 사용하지 않음 | 확정 정책 |

### 선택 이유

- v2.5의 핵심은 강한 손실 규칙이 아니라 사용자가 스스로 만든 시작 약속에 개입하는 것이다.
- 일정 변화에 대응할 수 있도록 시작 전 수정·취소를 허용한다.
- 반복적인 시간 이동만으로 개입을 무기한 회피하지 않도록 정규 수정은 1회로 제한한다.
- 시작시간이 지난 뒤 시간을 수정하거나 취소하면 실제 개입 결과를 사후 변경할 수 있어 행동검증 데이터 해석이 어려워지므로 허용하지 않는다.

### 수정 후 시간 조건

수정된 시작시간도 다음 조건을 모두 만족해야 한다.

- 수정 시점 기준 최소 +30분
- 수정 시점 기준 최대 +72시간
- 행동검증 종료시각 이전
- 행동검증 기간의 `동일 예정 시작일(KST)당 1개 약속` 원칙 충족

수정·취소는 모두 행동 이벤트로 기록한다.

# 3. 시작 개입 및 재알림 정책

## 3.1 전체 시간 구조

| 단계 | 기준 시각 | 상태 |
|---|---:|---|
| 시작 알림 | 약속 시작시간 T | 확정 정책 |
| 1차 재알림 | T + 10분 | 초기 운영값 |
| 2차 재알림 | T + 20분 | 초기 운영값 |
| 인증 가능 종료 | T + 30분 | 초기 운영값 |

### 선택 이유

- 기존 3회 재알림은 포인트 손실 단계와 결합되어 있었으므로 v2.5에서 그대로 유지할 근거가 약하다.
- 1회만 제공하면 단순 놓침에 대한 회복 기회가 적어, 초기 MVP에서는 2회로 시작한다.
- 10분 간격은 기존 운영값을 재사용해 새로운 가정을 최소화하면서 동일한 시작 맥락 안에서 다시 상기시키기 위한 초기값이다.
- T+30분 이후까지 인증을 허용하면 ‘계획한 시작 시점에 대한 개입’보다 넓은 당일 인증으로 의미가 흐려질 수 있어 초기 종료선으로 30분을 사용한다.

> `2회 / 10분 / 30분`은 최적값으로 검증된 수치가 아니다. 행동검증 전까지 UT 및 QA에서 과도한 알림 부담이나 기술적 문제가 확인되면 조정할 수 있다.

## 3.2 재알림의 역할

재알림은:

> **아직 인증하지 않은 사용자에게 인증 가능 상태와 시작 행동을 다시 상기시키는 리마인드**

다.

재알림은 새 인증 권한이나 새 인증 세션을 부여하지 않는다.

### 공통 규칙

- T부터 T+30분까지 인증 가능 상태를 유지한다.
- 사용자는 재알림을 기다리지 않고 인증 가능 시간 안에 자발적으로 다시 인증 화면에 진입할 수 있다.
- 이미 인증 완료한 약속에는 이후 재알림을 발송하지 않는다.
- 인증 가능 종료 시각에 미인증 상태이면 `인증 미완료`로 종료한다.
- 인증 미완료 자체에 포인트·등급·기타 손실을 부여하지 않는다.
- 참가자는 재알림 간격이나 횟수를 직접 변경할 수 없다.

# 4. 인증 카테고리 정책

| 항목 | 정책 |
|---|---|
| 지원 카테고리 | 컴퓨터 / 책 |
| 컴퓨터 범위 | 노트북, 데스크탑, 외부 모니터 |
| 자유 입력 카테고리 | 제공하지 않음 |
| 태블릿·전자책 단말기 | MVP 기본 카테고리에서 제외 |
| 기타 카테고리 확장 | 이번 MVP에서 하지 않음 |

### 판별 예시

| 촬영 대상 | 처리 |
|---|---|
| 모니터 또는 노트북이 식별 가능 | 컴퓨터 인증 가능 |
| 전원이 꺼진 컴퓨터 | 컴퓨터 인증 가능 |
| 실제 책이 식별 가능 | 책 인증 가능 |
| 화면에 표시된 책 이미지 | 책 인증 불가 |
| 태블릿·전자책 단말기만 존재 | 기본 카테고리 인증 불가 |

### 원칙

- 이번 인증의 목적은 작업 완료 증명이 아니라 작업도구가 있는 환경으로의 이동을 요구하는 것이다.
- 작업 내용·화면 내용·책 제목의 적절성은 판단하지 않는다.
- 사용자의 작업 품질이나 실제 작업 시작 여부를 이미지 판정으로 추론하지 않는다.

# 5. 사진 인증 및 재시도 정책

## 5.1 재시도 원칙

| 항목 | 정책 | 상태 |
|---|---|---|
| 제출 전 재촬영 | 제한 없음 | 확정 정책 |
| 판정거절 후 재촬영·재제출 | 인증 가능 시간 내 허용 | 확정 정책 |
| 사용자 판정 횟수 제한 | 두지 않음 | 확정 정책 |
| 기술오류 | 사용자 실패로 처리하지 않음 | 확정 정책 |

### 선택 이유

- 이번 사진 인증의 목적은 부정행위 방지보다 사용자를 작업도구가 있는 환경으로 이동시키는 데 있다.
- 판정거절 횟수를 제한하면 AI 오판정 때문에 실제 시작 행동을 시스템이 방해할 수 있다.
- 한 화면 3회 제한 후 재진입을 허용하는 구조는 실질적인 전체 제한 효과는 적으면서 상태·UI·구현 복잡도만 증가한다.
- 악의적 반복 요청이나 비용 문제는 사용자 정책이 아니라 개발팀의 기술적 요청 제한으로 관리한다.

## 5.2 판정 결과

모든 사진 제출은 아래 중 하나로 처리한다.

1. 인증 성공
2. 판정거절
3. 기술오류

| 결과 | 처리 |
|---|---|
| 인증 성공 | 인증 완료 기록 → 해당 약속의 시작 개입 종료 |
| 판정거절 | T+30 이전이면 재촬영·재제출 가능 |
| 기술오류 | 사용자 실패로 처리하지 않고 복구 경로 제공 |
| 복구 불가능한 기술오류 | 기술 실패 종료 |

### 인증 가능 종료 경계

- T+30 전에 서버에 정상 접수된 유효 제출은 판정 완료까지 결과를 기다린다.
- T+30 이후에는 신규 제출을 허용하지 않는다.
- T+30 전에 접수된 제출이 판정거절된 시점에 이미 T+30을 지났다면 추가 재제출 없이 인증 미완료로 종료한다.
- 기술오류로 판정이 불가능한 경우에는 기술오류 정책을 적용한다.

# 6. 이미지 판정 QA 원칙

본 정책문서는 AI 모델의 정확도 수치나 threshold를 직접 확정하지 않는다.

### 제품 요구조건

- 컴퓨터 / 책 카테고리를 행동검증에 사용할 수 있을 정도로 일관되게 판별할 수 있어야 한다.
- 오거절이 반복되어 사용자의 실제 시작 행동을 방해할 정도여서는 안 된다.
- 부적절한 이미지가 지나치게 쉽게 통과해 인증 행동의 의미가 사라져서는 안 된다.
- 행동검증 시작 전 실제 MVP 사용환경을 반영한 샘플로 QA를 수행한다.

### 개발팀 결정

AI 엔지니어와 개발팀은 별도 AI QA 기준에서 아래를 정의한다.

- 테스트 샘플 구성
- 모델 입력 조건
- 출력값
- 성공/거절 threshold
- 오수용·오거절 판단 기준
- 모델 버전
- 행동검증에 사용할 수 있는 수준인지에 대한 기술 판단

# 7. 알림·카메라 권한 정책

## 7.1 공통 원칙

- 알림 권한과 카메라 권한은 이번 행동검증의 핵심 기능을 사용하기 위한 필수 조건이다.
- 모집 또는 온보딩 단계에서 권한 필요성을 사전에 안내한다.
- 권한 거부 자체를 사용자 실패, 인증 미완료의 원인으로 자동 해석하지 않는다.
- 권한을 최종 확보하지 못한 참가자는 핵심 행동검증 분석 대상에서 제외한다.

## 7.2 알림 권한

### 최초 온보딩

1. 시작시간 알림이 행동검증에 필요한 이유를 안내한다.
2. 사용자가 알림 권한 설정을 진행한다.
3. 거부되면 복구 방법을 안내한다.
4. 정상 알림 환경을 확보하지 못하면 행동검증 진행 대상에서 제외한다.

### 검증 중 권한 해제

- 권한 해제를 감지하면 복구 안내를 제공한다.
- 복구 전 발생한 약속의 행동 데이터는 권한 부재 영향을 별도 표시한다.
- 권한을 복구하지 못하면 이후 행동검증 참여를 종료할 수 있다.

## 7.3 카메라 권한

- 최초 사진 인증 시 카메라 사용 목적을 먼저 설명한다.
- 사용자가 촬영 동작을 실행할 때 권한을 요청한다.
- 거부된 경우 복구 방법을 안내한다.
- 권한 복구 전에는 사진 인증을 진행할 수 없다.
- 카메라 권한 거부를 판정거절이나 기술오류와 동일하게 처리하지 않는다.
- 지속적으로 카메라 사용이 불가능하면 행동검증 분석 대상에서 제외한다.

# 8. 기술오류 및 상태 복구 정책

## 8.1 기술오류 예시

- 사진 업로드 실패
- 서버 오류
- 이미지 판정 시간초과
- 내부 처리 실패
- 알림 발송 시스템 오류
- 상태 저장 실패

## 8.2 처리 원칙

- 기술오류는 사용자 미인증으로 판단하지 않는다.
- 기술오류 때문에 사용자의 인증 가능 시간이 부당하게 소진되지 않도록 복구 가능성을 우선한다.
- 기술오류 복구 후에는 저장된 마지막 정상 상태에서 계속한다.
- 자동 재시도·타임아웃·백오프 등 구체 구현 방식은 개발팀이 결정한다.

## 8.3 기술 실패 종료

복구 불가능한 기술문제로 해당 약속을 정상적으로 계속할 수 없는 경우 `기술 실패 종료`로 분리한다.

- 인증 완료/미완료 어느 쪽으로도 계산하지 않는다.
- 새 약속 생성은 허용한다.
- 행동 효과 지표 분석에서는 제외한다.
- 기술 실패율과 운영 품질 분석에는 포함한다.

## 8.4 앱 종료·재진입

- 앱을 종료하거나 브라우저를 이탈해도 활성 약속은 유지한다.
- 재진입 시 현재 상태를 복원한다.
- 재진입으로 재알림 시계 또는 인증 가능 종료시각을 초기화하지 않는다.
- 이미 인증 완료된 약속을 다시 미인증 상태로 되돌리지 않는다.

# 9. 시작 인증 기록 피드백 정책

## 9.1 표시 가능한 정보

- 최근 약속의 `인증 완료 / 인증 미완료`
- 필요 시 일정 기간의 `인증 완료 횟수 / 전체 종료 약속 수`

예:

> 이번 주 시작 인증 3 / 5

## 9.2 사용하지 않는 표현

시스템은 실제 작업 시작을 직접 확인하지 못하므로 아래 표현을 기본 지표로 사용하지 않는다.

- 약속 성공 / 실패
- 약속 지킴 / 어김
- 시작 성공률
- 작업 수행률

## 9.3 기술 실패·취소 처리

- 기술 실패 종료 약속은 인증 결과 집계에서 제외한다.
- 시작 전 사용자 취소 약속도 인증 결과 집계에서 제외한다.
- 수정된 약속은 최종 시작시간 기준 하나의 약속으로 집계한다.

# 10. 행동검증용 일일 자기보고 정책

> 본 항목은 정식 제품 핵심 기능이 아니라 실제 작업 시작 여부를 보조 측정하기 위한 검증 전용 요소다.

## 10.1 대상

- 전날 시작 개입이 종료된 약속이 있는 참가자
- 행동검증 기간 동안 KST 기준 동일한 예정 시작일에 최대 1개 약속만 허용하므로 자기보고와 해당 약속을 1:1로 연결한다.

## 10.2 노출·리마인드

| 항목 | 정책값 | 상태 |
|---|---:|---|
| 기본 노출 가능 시점 | 약속 다음날 00:00 이후 | 확정 정책 |
| 첫 서비스 진입 | 미작성 설문 1회 비강제 안내 | 확정 정책 |
| 알림 리마인드 | 다음날 11:00, 미응답 시 1회 | 초기 운영값 |
| 추가 푸시 알림 | 없음 | 확정 정책 |
| 응답 가능 기간 | 약속 다음날 00:00부터 48시간 | 초기 운영값 |
| 48시간 초과 | 미응답 종료 | 확정 정책 |

### 선택 이유

- 당일 인증 직후나 작업 중간에 설문을 보내면 측정이 새로운 작업 개입으로 작용하거나 집중을 방해할 수 있다.
- 다음날 회고 방식은 제품의 당일 시작 개입과 측정 접촉을 분리한다.
- 11:00은 너무 이른 아침을 피하면서 전날 경험과의 간격이 지나치게 길어지기 전 한 번만 회수 기회를 주기 위한 초기 운영값이다.
- 48시간 이후 응답은 회상 정확도 저하 가능성이 커져 보조 데이터 품질이 낮아질 수 있어 미응답으로 종료한다.

## 10.3 사용자 통제

- 설문은 언제든 건너뛸 수 있다.
- 설문을 작성하지 않아도 다음날 이후 새 약속을 생성할 수 있다.
- 설문 미작성에 보상·손실·등급 변화가 없다.
- 미응답을 실제 작업 미시작으로 계산하지 않는다.
- 설문 응답 여부를 인증 완료/미완료 상태에 반영하지 않는다.

## 10.4 기본 문항

1. [예정 시작일시]의 시작 약속 이후 실제 작업을 시작했나요?
   - 예
   - 아니오

2. `예`인 경우: 인증 후 언제쯤 실제 작업을 시작했나요?
   - 바로 시작함
   - 5분 이내
   - 15분 이내
   - 15분 이후

3. `아니오`인 경우: 시작하지 못한 이유와 가장 가까운 것은 무엇인가요?
   - 피로·컨디션
   - 다른 일정 발생
   - 하기 싫음·흥미 부족
   - 인증 후 다른 행동으로 이탈
   - 기타

실제 화면에서는 1번 응답에 따라 2번 또는 3번 중 하나만 노출할 수 있다.

## 10.5 해석 원칙

- 자기보고는 실제 작업 시작을 보조 확인하는 자료이며 시스템 로그와 분리한다.
- 미응답은 미시작으로 간주하지 않는다.
- 반복 자기보고가 사용자의 행동 인식에 일부 영향을 줄 가능성을 분석 한계로 기록한다.

# 11. 사진 저장·보관 정책

| 항목 | 정책 |
|---|---|
| 사진 최대 보관기간 | 행동검증 공식 종료일로부터 30일 |
| 삭제 | 보관기간 종료 후 삭제 |
| 참가자 삭제 요청 | 보관기간과 무관하게 해당 참가자와 연결된 사진 삭제 |

### 제품·운영 요구조건

- 사진은 인증 및 행동검증 목적을 넘어 사용하지 않는다.
- 외부에 공개적으로 접근 가능한 상태로 제공하지 않는다.
- 참가자에게 이미지 수집 목적과 보관기간을 사전 고지한다.
- 삭제 요청 시 해당 참가자와 연결된 사진과 관련 연결정보를 삭제할 수 있어야 한다.
- 이미지 저장 위치·파일 키·암호화·삭제 구현 방식은 개발팀이 결정한다.

# 12. 참가자 식별 정책

| 항목 | 정책 |
|---|---|
| 정식 회원가입 | 사용하지 않음 |
| 참가자 식별 | 참가자별 고유한 식별 방식 사용 |
| 분실·재발급 | 기존 식별정보의 안전한 폐기 후 재발급 가능 |

### 제품·운영 요구조건

- 다른 참가자가 타인의 데이터에 접근할 수 없어야 한다.
- 분실된 기존 접근정보는 재발급 후 사용할 수 없게 해야 한다.
- 식별 방식의 구체 형식·길이·저장·암호화 방식은 개발팀이 결정한다.

# 13. 행동 데이터 보관·삭제 정책

## 13.1 수집 범위

행동검증에 필요한 최소 원본 데이터만 수집한다.

세부 이벤트·필드는 `로그-검증 매핑표`에서 확정한다.

대표 범위:

- 약속 생성·수정·취소
- 최종 시작시간
- 시작 알림·재알림
- 인증 화면 진입
- 사진 제출·판정
- 인증 완료시각
- 최종 인증 상태
- 권한 상태
- 기술오류
- 인증 기록 피드백 확인
- 자기보고 응답

## 13.2 보관기간

| 항목 | 정책 |
|---|---|
| 참가자 연결 행동 원시 데이터 최대 보관 | 행동검증 종료 후 90일 |
| 참가자 식별 연결 | 분석에 필요한 기간만 유지 |
| 90일 종료 후 | 참가자와 다시 연결 가능한 원시 행동 데이터 삭제 |
| 비식별 집계 결과 | 개인과 다시 연결할 수 없는 형태라면 유지 가능 |

## 13.3 중도 철회

참가자가 철회를 요청하면 그 시점부터 새로운 행동 데이터 수집과 제품 개입을 중단한다.

- 예약된 알림·재알림 취소
- 활성 약속은 인증 미완료로 처리하지 않고 `참여 철회 종료`로 분리
- 철회 이후 도착한 비동기 처리 결과를 참가자 행동 결과에 반영하지 않음
- 참가자 접근 비활성화
- 철회 전 데이터는 별도의 삭제 요청이 없다면 기존 보관정책 적용

## 13.4 기존 데이터 삭제 요청

참가자가 과거 데이터 삭제까지 요청한 경우 참가자와 연결 가능한 원시 데이터를 삭제하고 이후 개별 분석에서도 제외한다.

삭제 대상:

- 사진
- 행동 이벤트 원시 데이터
- 자기보고 개별 응답
- 참가자 식별 연결 정보

개인과 다시 연결할 수 없는 기존 비식별 집계 결과는 유지할 수 있다.

- 카메라 촬영
- 사진 업로드
- 상태 저장·복원

## 14.2 지원 환경 확정 시점

구체적인 지원 기기·OS·브라우저 목록은 Sprint 기술 검토 및 내부 QA 후 행동검증 시작 전에 확정한다.

지원 목록에 포함되지 않은 환경에서의 오류를 사용자 행동 실패로 해석하지 않는다.

# 15. 참가자 사전 고지

행동검증 시작 전 최소한 아래 내용을 안내한다.

- 본 서비스가 개인작업의 ‘시작 행동’을 검증하기 위한 MVP라는 점
- 시작시간 알림 및 재알림 방식
- 사진 인증의 목적과 사용 방식
- 사진 인증 성공이 실제 작업 시작 확인을 의미하지 않는다는 점
- 알림·카메라 권한 필요
- 촬영 이미지와 행동 데이터 수집
- 사진 및 행동 데이터 보관기간
- 다음날 행동검증용 자기보고가 제공된다는 점
- 자기보고 응답은 선택이며 서비스 결과에 영향을 주지 않는다는 점
- 참여 철회 및 기존 데이터 삭제 요청 방법

## 16.1 행동검증 시작 전 조정 가능

디자인 UT·내부 QA 결과에 따라 다음 초기 운영값은 조정할 수 있다.

## 16.2 행동검증 시작 이후 동결

다음 조건은 원칙적으로 동일하게 유지한다.

- 예약 가능 범위
- 하루 약속 수

1. 변경 시점 기록
2. 변경 전·후 참가자/데이터 구분
3. 분석에서 동일 조건 데이터처럼 단순 합산하지 않음
